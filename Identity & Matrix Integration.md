# PhotoBunker — Identity & Matrix Integration

## Задача

Мы меняем архитектурную концепцию PhotoBunker. Приложение должно строиться вокруг полноценного пользовательского аккаунта с постоянным ID, анкетой и возможностью защищённого взаимодействия с другими пользователями.

Для переписки и звонков используем **Matrix**. Собственный протокол мессенджера не разрабатываем.

**Важно:** не переписывать приложение с нуля. Сначала изучить текущую ветку `codex/profile-first-app`, все существующие PR, `_docs` и `IMPLEMENTATION_PLAN.md`. Сохранить пригодные компоненты, тесты, API и инфраструктуру.

Создавать новые PR поверх актуальной цепочки веток. Не изменять `main` напрямую, не сливать PR самостоятельно.

## 1. Новая модель аккаунта

`User Account` становится основой всей системы.

Каждый пользователь имеет:

- Постоянный внутренний UUID и отдельный публичный ID.
- Псевдоним, аватар, необязательное описание.
- Приватные настройки профиля и видимости.
- Список контактов.
- Связанный Matrix ID.
- Устройства, механизмы восстановления и настройки безопасности.
- Собственные фотографии, настройки камеры, задания и участие в командах.

Email, номер телефона и настоящее имя не должны быть обязательными.

Разделить понятия:

- **User Profile** — профиль человека.
- **Camera Preset** — сохранённые настройки камеры; переименовать нынешние Profiles.
- **Assignment** — задание с требованиями и участниками.
- **Team** — постоянная команда с общей организацией доступа.

Для работы приложения не должно требоваться создание собственного Camera Preset или Team вручную.

Один PhotoBunker Account связывается с одним Matrix ID; несколько устройств принадлежат этому аккаунту. Внутренний PhotoBunker ID остаётся главным идентификатором продукта.

## 2. Matrix Infrastructure

Использовать:

- **Tuwunel** — Matrix homeserver, вместо Conduit.
- **matrix-js-sdk** с Rust/WASM crypto — интеграция с Vue.
- **MatrixRTC + LiveKit + lk-jwt-service** — современная инфраструктура звонков.
- **Coturn** — только при подтверждённой необходимости для legacy/P2P WebRTC или как внешний TURN для LiveKit.

Развёртывание через Docker Compose, с отдельными сервисами, volumes и конфигурацией.

Требования:

1. Не заменять существующий Laravel backend Matrix-сервером.
2. Не использовать matrix.org как обязательный сервис.
3. Закрыть публичную самостоятельную регистрацию на Matrix; аккаунты создавать только через контролируемый механизм PhotoBunker.
4. Проверить документированную и безопасную схему автоматического создания Matrix-аккаунта, авторизации, привязки и отзыва устройств.
5. Не создавать вторую видимую форму регистрации или отдельный вход в Matrix.
6. Все служебные секреты хранить вне Git; не передавать секреты администрирования в браузер.
7. Для тестов использовать отдельные временные Matrix ID. Постоянный `server_name` выбрать осознанно: он влияет на идентификаторы пользователей.
8. Федерацию на ранней стадии можно отключить, но архитектура не должна запрещать её последующее включение.
9. Не хранить содержимое переписки в PostgreSQL PhotoBunker и не реализовывать второй движок сообщений.
10. Предусмотреть резервное копирование, обновления, состояние здоровья сервисов и ограничения потребления ресурсов.

Сохранить существующий Garage/S3 как хранилище фотографий. Не отправлять оригиналы PhotoBunker в Matrix Media Repository.

## 3. Account & Matrix Identity

Разработать единый пользовательский сценарий:

Создать аккаунт PhotoBunker → получить постоянный ID → автоматически получить Matrix-аккаунт → начать общение.

Пользователь не должен разбираться в homeserver, MXID или двух разных наборах паролей.

Однако единый UX не должен приводить к хранению сервером приватных ключей E2EE в открытом виде.

Обязательно:

- Сопоставление PhotoBunker UUID ↔ Matrix ID.
- Защищённые сессии.
- Проверка устройств, cross-signing, Matrix secret storage и key backup.
- Recovery Key и понятное восстановление на новом устройстве.
- Отзыв сессий и устройств.
- Защита от повторного создания одного Matrix-аккаунта при сбое.
- Отдельное объяснение, какие данные профиля видит Matrix-сервер.

**Не считать обычный PIN достаточной защитой криптографических ключей.**

Если надёжный единый механизм восстановления PhotoBunker и Matrix не получается реализовать сразу, сначала документировать ограничение. Не создавать иллюзию, что один Recovery Key уже восстанавливает всё.

## 4. Contacts & Messaging

Реализовать полноценную встроенную систему сообщений через Matrix SDK.

Первоначальный функционал:

- Поиск человека по PhotoBunker ID.
- Просмотр его анкеты в пределах настроек приватности.
- Запрос на добавление контакта / приглашение в переписку.
- Принятие и отклонение приглашений.
- Блокировка пользователя.
- Личные E2EE-переписки.
- Групповые E2EE-комнаты.
- Отправка, получение, история и синхронизация сообщений.
- Ответы на сообщения.
- Индикаторы доставки и прочтения, где это действительно поддерживается.
- Уведомления без раскрытия приватного текста на заблокированном устройстве.
- Восстановление доступа к истории после смены устройства при наличии ключей.

Использовать официальные возможности Matrix. Не разрабатывать собственный протокол E2EE.

Не добавлять публичные ленты, подписчиков, лайки или полноценную социальную сеть.

## 5. Calls

Проверить и реализовать интеграцию аудио- и видеозвонков через совместимые MatrixRTC-компоненты.

Цель — личные и групповые звонки непосредственно внутри PhotoBunker.

Не считать Coturn готовым решением для MatrixRTC: исследовать LiveKit, JWT authorization и поддерживаемые средства WebRTC connectivity.

Проверить:

- Вызов между двумя браузерами.
- Вызов между мобильным и десктопным клиентами.
- Микрофон и камеру, отключение и завершение вызова.
- Сетевые ограничения, TURN и NAT.
- Заявляемую E2EE-защиту медиапотоков.
- Поведение установленной PWA на iPhone и ограничения входящих вызовов в фоне.

Не объявлять звонки полностью готовыми без реального end-to-end теста.

Если реализация звонков требует отдельного PR, отделить её от первого рабочего E2EE-чата, сохранив техническую совместимость.

## 6. Assignments & Teams

Не переносить всю логику приложения в Matrix.

PhotoBunker отвечает за создание заданий, правила, роли, фотографии, права на материалы и сроки хранения.

Matrix отвечает за коммуникации.

Team содержит владельца и постоянных участников.

Assignment содержит куратора, исполнителей и наблюдателей. У каждого задания может быть связанная Matrix-комната для обсуждения, но доступ к комнате и доступ к фотографиям — отдельные разрешения.

При приглашении пользователя в Assignment система должна автоматически создать необходимые связи и предоставить строго ограниченный доступ.

Contributor с режимом upload-only не должен получать ключи чтения чужих фотографий.

Для сообщений о фотографиях использовать ссылки/идентификаторы PhotoBunker, а не пересылать оригинальные изображения через Matrix.

Удаление фотографии по TTL должно блокировать доступ к ней даже при сохранении старого сообщения со ссылкой.

## 7. UI/UX

Нынешний интерфейс слишком похож на традиционный веб-сайт. Не развивать эту модель дальше.

PhotoBunker — устанавливаемая PWA с поведением мобильного приложения.

Основные пользовательские разделы:

- Camera —(*отдельный полноэкранный режим???)
- Assignments — задания, участники и материалы.
- Messages — переписки и звонки.
- Photos — личная галерея и доступные фотографии.
- Profile — анкета, контакты, команды и настройки.

Camera Presets и управление Teams не должны занимать постоянное место в основном Dock.

Сохранить настраиваемый стартовый экран, режим PIN перед галереей и настройками, тихий затвор, Quick Capture, GPS с последующим уточнением и предупреждения о незагруженных фотографиях.

Регистрация пользователя и настройка Matrix не должны превращать запуск камеры в длинный процесс onboarding.

## 9. Порядок работы и результат

Сначала обновить архитектурную документацию в `_docs`, зафиксировать Identity/Matrix integration и пересмотреть текущий `IMPLEMENTATION_PLAN.md`.

Далее самостоятельно разделить изменения на связанные PR с работающими результатами:

1. Собственный Matrix-сервер, конфигурация Docker и проверка API.
2. Аккаунт PhotoBunker, автоматическая привязка Matrix ID, безопасная авторизация.
3. Реальная E2EE-переписка и восстановление ключей.
4. Интеграция сообщений с Assignments.
5. Звонки и соответствующие проверки.

Это ориентиры декомпозиции, а не требование делать ровно пять PR.

Каждый PR должен содержать реальные тесты, описание проверки и честный перечень незавершённых возможностей. Не заменять работающий сценарий демонстрационными кнопками.

**Главное требование:** создать связанную систему пользователей и коммуникаций, не потеряв первоначальную идею PhotoBunker — мгновенная камера, зашифрованные фотографии, приватность и удобная совместная работа.
