# PhotoBunker — правила работы агента

Перед изменениями прочитать `README.md`, `docs/IMPLEMENTATION_PLAN.md` и ближайший `AGENTS.md` для затрагиваемого каталога.

## Приоритет

Рабочий пользовательский сценарий важнее количества PR, тестов и отчётов. Текущий главный блокер описан в разделе P0 единого плана: владелец должен вручную пройти реальную переписку между двумя аккаунтами.

## Обязательные правила

1. Делать Local-First и Optimistic UI: локальный результат появляется сразу, сеть работает в фоне.
2. Сначала надёжно сохранить операцию локально, затем отправлять её с постоянным idempotency key.
3. Обрабатывать offline, retry/backoff, cancellation, race conditions, временные ID, дубликаты и смену аккаунта.
4. Не блокировать новые сообщения recovery старой истории или подтверждением другого устройства.
5. Не показывать внутренние Matrix/crypto состояния в обычном пользовательском пути.
6. Не заявлять готовность по сборке или synthetic tests. Сначала ручная проверка владельца, затем целевые тесты.
7. Не запускать широкие тестовые матрицы, пока владелец не может пройти изменённый happy path.
8. Не создавать PR и новые ветки без прямого запроса. При явной команде `push main` коммитить весь указанный владельцем scope и отправлять прямо в `main`.
9. Сохранять чужие изменения рабочего дерева. Не восстанавливать намеренно удалённые документы.
10. Не создавать новые roadmap/ADR/status-документы без необходимости. Обновлять единый `docs/IMPLEMENTATION_PLAN.md`.

## Мессенджер

- Единственный backend сообщений PhotoBunker — Matrix/Tuwunel; Laravel не хранит вторую ленту сообщений.
- Chatify v2 — источник UI/UX-паттернов, не auth, backend, migrations или crypto.
- Plaintext сообщений, media keys и закрытых данных не отправлять в логи, аналитику, server search или `localStorage`.
- Каждый send имеет одну optimistic bubble и один стабильный transaction ID до ACK/reconnect.
- Отправка с потерянным ответом не должна создавать второе событие.
- `Sent`, `Delivered` и `Read` показывать только по фактическому состоянию Matrix.
- Room creation, UI preferences и recovery не должны блокировать composer или durable outbox.

## Порядок работы

1. Воспроизвести конкретный пользовательский дефект.
2. Найти источник истины и точную точку отказа.
3. Исправить минимальный целостный путь, не расширяя scope.
4. Проверить typecheck и узкую диагностику, достаточную для безопасной ручной проверки.
5. Сразу передать результат владельцу на ручную проверку.
6. После принятия добавить целевые regression tests на найденную причину.

Не оставлять владельцу технические обходные пути, команды консоли или обязательную очистку данных, если приложение может восстановиться автоматически.
