# PhotoBunker

PhotoBunker — устанавливаемое Local-First PWA для приватной съёмки, хранения и обработки фотографий, совместных заданий и защищённого общения.

Основная навигация приложения: **Задания · Сообщения · Камера · Фото · Профиль**.

## Что уже реализовано

- постоянный аккаунт PhotoBunker без обязательных телефона и email;
- профиль, публичный ID/username, контакты, блокировки и управление устройствами;
- камера, пресеты, категории, геометки и локальная очередь снимков;
- зашифрованное хранение фотографий, галерея, редактор, версии и приватные ссылки;
- команды, приглашения, задания, роли и назначение участников из контактов;
- личные и групповые Matrix-комнаты с E2EE;
- optimistic-отправка сообщений и зашифрованный durable outbox в IndexedDB;
- вложения, голосовые сообщения и MatrixRTC/LiveKit-звонки;
- RU/EN, светлая/тёмная тема и PWA-оболочка.

Большая часть функций реализована, но приложение ещё не считается production-ready. Первые критерии приёмки — рабочие регистрация/вход и обычная переписка между двумя реальными аккаунтами: открыть диалог, отправить и получить текст, повторить offline/reload/reconnect без потерь и дублей. Сборка и автоматические проверки эту приёмку не заменяют.

25 октября аудит выявил ранние блокеры входа и базовой переписки. Их технические исправления уже интегрированы, но перечисленные реализации не означают финальную пользовательскую приёмку. [Аудит](docs/AUDIT-20261025.md) и [чеклист](docs/CHECKLIST.md) задают требования, [IMPLEMENTATION_PLAN](docs/IMPLEMENTATION_PLAN.md) — архитектуру и долгосрочный roadmap, а единственная текущая очередь находится в [GitHub Issues](https://github.com/1troitsky/photobunker/issues) и Project **PhotoBunker Development**.

## Принцип работы

PhotoBunker проектируется как **Local-First & Optimistic UI**:

- действие сразу отражается в интерфейсе;
- операция сначала надёжно сохраняется локально, затем синхронизируется в фоне;
- offline, retry, reload и потерянный ответ не должны терять или дублировать данные;
- серверные идентификаторы заменяют временные без второго элемента в UI;
- старый ответ, смена аккаунта или комнаты не могут изменить текущий экран;
- статусы `Sent`, `Delivered`, `Read` и `Uploaded` показываются только после подтверждения источником истины.

Сообщения хранятся и синхронизируются через Matrix/Tuwunel. Laravel не содержит параллельную таблицу переписки. Chatify v2 используется только как источник UI/UX-паттернов; требования к общему messenger UI сохранены в [docs/references/artefacts-messages](docs/references/artefacts-messages/README.md).

## Архитектура

| Компонент | Назначение |
| --- | --- |
| `apps/web` | Vue 3, TypeScript, Vite, PWA, IndexedDB |
| `apps/api` | Laravel 13, Identity/Workspace/Photo API |
| PostgreSQL 17 | данные приложения и очереди Laravel |
| Garage 2.4 | private S3-compatible object storage |
| Tuwunel 1.9 | Matrix, комнаты, E2EE и receipts |
| LiveKit | аудио- и видеозвонки MatrixRTC |
| Nginx | единый локальный origin для web и API |

Для фотографий используются client-side encryption, неизменяемые оригиналы и отдельные encrypted objects для preview, thumbnail и версий. Для сообщений ключи и plaintext не должны попадать в Laravel, URL, аналитику или `localStorage`.

## Локальный запуск

Нужны:

- Node.js 22;
- Git;
- Docker Engine с Compose v2; на macOS удобно использовать OrbStack.

Первичная настройка из корня репозитория:

```sh
./scripts/dev setup
./scripts/dev matrix
```

Открыть [http://localhost:8080](http://localhost:8080). При работающем OrbStack также доступен `https://photobunker.orb.local`.

Обычный повторный запуск:

```sh
./scripts/dev up
./scripts/dev matrix
```

Звонки запускаются отдельно:

```sh
./scripts/dev rtc
```

Состояние и остановка:

```sh
./scripts/dev status
./scripts/dev down
```

`down` сохраняет данные именованных volumes PostgreSQL, Garage и Matrix.

## Ручная проверка переписки

1. Запустить приложение и Matrix командами выше.
2. Войти в два разных аккаунта в изолированных профилях браузера.
3. Добавить контакт или открыть его профиль и нажать «Написать».
4. Убедиться, что поле ввода доступно сразу, без требования восстановить старую историю.
5. Отправить текст и увидеть один optimistic bubble.
6. Получить сообщение во втором аккаунте и ответить.
7. Проверить offline → отправка → reload → online: сообщения должны дойти ровно по одному разу.

Если этот сценарий не проходит, мессенджер не принят независимо от результатов CI.

## Технические проверки

Codex запускает целевые проверки при доработке PR. Полные команды ниже используются по риску и перед релизом; ручная проверка владельцем на телефоне запланирована после завершения работ и развёртывания на удалённом сервере:

```sh
./scripts/dev smoke
./scripts/dev messenger-smoke
./scripts/dev check
```

- `smoke` проверяет инфраструктуру и HTTP, но не доказывает работу переписки;
- `messenger-smoke` проверяет первый E2EE-диалог двумя браузерными аккаунтами;
- `check` запускает проверки API, форматирование, web tests, typecheck и сборку.

## Структура репозитория

```text
apps/web/                           Vue/PWA клиент
apps/api/                           Laravel API и миграции
infra/                              Docker, Nginx, Garage, Matrix, LiveKit
scripts/                            локальное управление окружением
contracts/                          фактические API/format contracts
.github/ISSUE_TEMPLATE/task.yml     единая форма новых задач
.github/pull_request_template.md    обязательная передача реализации
docs/IMPLEMENTATION_PLAN.md         продукт и архитектурный roadmap
docs/references/artefacts-messages/ справочные требования messenger UI
tools/browser-spike/                узкие browser/E2EE проверки
AGENTS.md                           правила работы автоматизированных агентов
CHATBOT-AGENTS.md                   правила работы Chatbot через отдельные PR
COLLABORATION.md                    роли, Scrumban, WIP и критерии стадий
docs/REMEDIATION_PLAN-20261025.md   архив перехода от аудита к Issues
```

Локальные `.env` и credentials не коммитятся. В репозитории остаются только `.env.example`, lockfiles и конфигурация без секретов.

## Документация

Поддерживаются два основных документа:

1. этот `README.md` — описание приложения, архитектуры и запуска;
2. [docs/IMPLEMENTATION_PLAN.md](docs/IMPLEMENTATION_PLAN.md) — продукт, архитектура и долгосрочные требования.

Неактуальные параллельные планы, исторические ADR, отчёты и runbook-дубли удалены. Контракты рядом с кодом и справочные messenger-артефакты сохраняются только там, где они описывают действующее поведение.

Аудит и CHECKLIST остаются требованиями, а старый remediation plan — только архивом выполненного перехода. Операционные карточки, зависимости и критерии приёмки хранятся только в GitHub Issues; стадия — в Project. Совместная работа: Chatbot Agent пишет код через Draft PR, Codex проверяет, дорабатывает и интегрирует, владелец принимает на реальном устройстве. Правила: [COLLABORATION.md](COLLABORATION.md) и [CHATBOT-AGENTS.md](CHATBOT-AGENTS.md).
