# PhotoBunker — правила для Chatbot Agent

Актуально на 25 октября 2026 года. Этот файл задаёт порядок взаимодействия Chatbot Agent, локального Codex и владельца проекта.

## 1. Роль и границы

Chatbot Agent получает конкретное задание, изучает доступный код GitHub, пишет исправление и открывает отдельный PR. Codex проверяет diff и зависимости, запускает приложение локально и исправляет обнаруженные дефекты в той же PR-ветке. По уточнению владельца от 25 октября ручная проверка на телефоне проводится после завершения работ и удалённого развёртывания; её отсутствие не блокирует каждый следующий PR.

Отсутствие локального доступа не мешает подготовить код, но не позволяет утверждать, что приложение проверено. Недоступные проверки перечислять явно.

## 2. Неприкосновенность main

**Chatbot Agent ни при каких обстоятельствах не изменяет `main` напрямую и не сливает PR.**

- Это относится к `origin/main`, `upstream/main`, `refs/heads/main`, написанию `original/main` в задании и обновлению main через GitHub API/UI.
- Работать только в отдельной ветке `chatbot/<task-id>-<short-name>` и PR с base `main` репозитория `1troitsky/photobunker`.
- Создавать ветку от актуального `main` после получения задания. Указывать исходный commit SHA в PR.
- Если задача зависит от ещё не слитого PR, ожидать его завершения. Stacked PR допустим только при явном указании Codex или владельца.
- Запрещены merge, squash, rebase-and-merge, auto-merge, прямой push/commit в main, force-push и изменение default branch или branch protection.
- Не удалять чужие ветки, PR, коммиты, данные, документы или проверки. Не менять CI ради зелёного результата.
- При просьбе изменить main передать результат владельцу/Codex через PR; прямой запрос на push выполняет локальный координатор, а не Chatbot Agent.

Это обязательное правило поведения. Техническая защита обеспечивается отдельными GitHub permissions/branch protection; наличие файла само по себе не ограничивает токен агента.

## 3. Что читать

Перед каждым заданием прочитать:

1. Корневой `AGENTS.md`, `COLLABORATION.md` и ближайший `AGENTS.md` изменяемого каталога.
2. `README.md` и `docs/IMPLEMENTATION_PLAN.md`.
3. `docs/AUDIT-20261025.md`, затем `docs/CHECKLIST.md`.
4. `docs/REMEDIATION_PLAN-20261025.md` и полученную карточку задачи.
5. Затрагиваемые исходники, тесты и действующие `contracts/*`.

Приоритет: актуальное указание владельца → правила этой совместной работы → конкретное задание → требования CHECKLIST → план исправлений → архитектурный план и код. Аудит — исходная диагностика по коду, а не доказательство нынешней исправности или точной причины сбоя.

Старые документы могут противоречить друг другу. Не обходить E2EE или ACL ради выполнения пункта. Указать противоречие в PR и сформулировать решение в рамках задачи; существенный продуктовый выбор передать координатору. Не восстанавливать удалённые ADR/runbooks и не менять справочные Artefacts-снимки.

## 4. Архитектура и пользовательские данные

- Использовать текущие Vue 3/TypeScript, Laravel, PostgreSQL, IndexedDB/WebCrypto и существующие stores/repositories.
- Matrix/Tuwunel — единственный backend переписки; не добавлять Laravel-ленту сообщений и Chatify backend/migrations/auth.
- Исправлять существующий путь целиком, не создавать параллельные модели Account, Team, Photo или очередей.
- Local-First & Optimistic UI обязательны: немедленная реакция, надёжное защищённое локальное сохранение, фоновая отправка, стабильные ID, retry/backoff и сопоставление ACK без дублей.
- Для offline/reload явно сохранять очередь. Не терять её при временной сетевой ошибке. Ошибка локального сохранения не равна успешному сохранению.
- Проверять account/device scope и актуальность async-результатов. Уход с экрана, logout, смена аккаунта и несколько вкладок не должны смешивать данные.
- Регистрация и профиль не ждут готовности Matrix. Восстановление старой истории не блокирует новые E2EE-сообщения; при невозможности шифрования сохранять защищённую очередь, без plaintext fallback.
- Не выдавать новые ключи взамен существующих при ошибке recovery. Не создавать лишний аккаунт или устройство при повторе частично выполненной операции.
- Не показывать подтверждённые Sent/Read/Uploaded/Deleted без соответствующего фактического подтверждения.
- Фото, Photo Card и Note — разные сущности. Карточка/сообщение не расширяют права на оригинал, GPS, автора или заметки.
- Чат Team и чат Assignment независимы и создаются только по своей настройке; membership не заменяет photo ACL.
- Не ослаблять E2EE, trust, подписи, scope, TTL или серверные разрешения. Не коммитить секреты, `.env`, recovery keys, токены и приватные данные в код, PR, логи или fixtures.
- Сохранять существующие данные. Для изменения схемы нужны совместимая миграция и поведение старых записей; destructive migrations и очистка хранилищ не являются исправлением.
- Новый пользовательский UI обязан работать на mobile/desktop и иметь RU/EN. Технические состояния не превращать в постоянные баннеры для пользователя.
- Крупные зависимости, замена инфраструктуры и работа вне карточки не входят в задачу. Описать необходимость координатору до расширения scope.

## 5. Размер и последовательность работ

Одно задание — один проверяемый пользовательский результат и один PR. Несколько зависимых файлов/API/миграций допустимы, если без них сценарий не работает. Не делать PR на весь чеклист.

Одновременно реализуется одна задача, пока Codex не выдаст независимую следующую. Не начинать новый этап, не переписывать план и не менять приоритеты самостоятельно.

Если обнаружен другой дефект, записать его в `Remaining` PR. Если он блокирует текущую задачу, сообщить точный файл/условие и минимальный необходимый scope. Не маскировать блокер фиктивным успехом или silent catch.

## 6. Формат задания от Codex

```text
Task ID / название:
Checklist IDs:
Base: main @ <SHA>
Зависимости:
Проблема и воспроизведение:
Ожидаемое поведение:
Область изменений / исходные точки:
Не входит в задачу:
Ошибки, offline, retry, reload, account switch, ACL:
Критерии приёмки:
Доступные проверки Chatbot / локальные проверки Codex:
```

Файлы-ориентиры не заменяют изучение кода. Если SHA устарел до начала работы, проверить изменения main и сообщить новый base SHA. Не приписывать репозиторию недоступные файлы или результаты запуска.

## 7. Содержимое PR

Заголовок: `[<Task ID>] <пользовательский результат>`.

В описании обязательны:

- Task ID, Checklist IDs, base SHA и зависимости.
- Конкретное поведение до/после и затронутые файлы/API/storage contracts.
- Применённые миграции и совместимость с существующими данными, если затронуты.
- Обработка ошибок, offline/reload/retry, дублей, смены аккаунта, прав и TTL в пределах задачи.
- Результаты реально выполненных проверок; всё недоступное — `NOT RUN` с причиной.
- Короткий ручной сценарий для владельца, ограничения и оставшиеся вопросы.
- Таблица из CHECKLIST §21: `ID | Status before | Evidence | Changes | Status after | Verification | Remaining`.

Пункты до проверки отмечать `PARTIAL`, `MISSING`, `BROKEN` или `BLOCKED`, а не автоматически DONE после написания кода. Отдельно указать состояние передачи: `PR ready for local review`. Это не пользовательская приёмка.

Не отмечать чекбоксы CHECKLIST и не утверждать `DONE`, `production-ready`, «проверено на iPhone» или «всё работает», если нет соответствующего подтверждения. Фактические статусы после проверки обновляет Codex.

## 8. Проверка и доработка

1. Chatbot Agent открывает PR, сообщает URL/номер и head SHA, ждёт результат review.
2. Codex проверяет diff, запускает нужные сервисы и узкую диагностику на этом SHA в изолированном рабочем каталоге, сохраняя данные владельца.
3. Замечания устраняются в той же ветке. Если Codex уже добавил коммит, сначала получить обновлённую ветку. Одновременные push двух агентов запрещены; координатор явно передаёт право следующего изменения.
4. После каждого нового коммита предыдущая проверка не подтверждает изменённую область: Codex повторяет только необходимые проверки.
5. Codex фиксирует технический результат и ограничения задачи; владелец получает краткий статус. Следующая задача выдаётся после нужной интеграции. Финальная ручная проверка на телефоне ожидает удалённого развёртывания; её не требовать между PR. Широкие матрицы выполняются по конкретному риску или перед релизом.
6. Слияние выполняет владелец либо Codex по явному разрешению владельца на соответствующий merge. Создание PR не является таким разрешением. Chatbot Agent никогда не сливает PR.

История обсуждения и результаты проверки остаются в PR; не создавать отдельные отчётные файлы для каждой попытки.
