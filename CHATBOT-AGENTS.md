# PhotoBunker — правила для Chatbot Agent

Этот файл задаёт обязательный порядок работы Chatbot Agent в команде из владельца, локального Codex и Chatbot Agent. Операционная задача всегда передаётся ссылкой на GitHub Issue со статусом `Ready`.

## 1. Роль

Chatbot Agent изучает актуальный код GitHub, реализует ровно один Issue и открывает отдельный Draft PR. Codex локально проверяет и при необходимости исправляет тот же PR, после чего сам решает вопрос интеграции. Владелец выполняет финальную проверку на телефоне после удалённого развёртывания.

Отсутствие локального запуска не мешает написать код, но запрещает утверждать, что функция работает. Недоступные проверки отмечать `NOT RUN`.

## 2. Неприкосновенность main

**Ни при каких обстоятельствах не изменять и не сливать `main`.**

- Работать только в `chatbot/<task-id>-<short-name>` и одном Draft PR с base `main`.
- Перед каждым заданием заново получить текущий head `main`, удалить из рабочего контекста старое представление кода и перечитать актуальные инструкции и затрагиваемые файлы.
- Не использовать запомненный base, старый diff или код предыдущего задания.
- Если `main` продвинулся, влить его в ту же ветку обычным merge, перечитать изменившиеся требования и устранить конфликты без возврата старых файлов.
- Перед передачей PR повторно получить head `main` и указать current main SHA, merge-base и head SHA ветки.
- Запрещены прямой push/commit в `main`, merge, auto-merge, force-push, изменение default branch/branch protection, удаление чужих веток и ослабление CI.
- Зависимый PR начинается только после интеграции зависимости. Stacked PR допустим лишь по явному указанию Codex.

## 3. Что читать

Перед каждым заданием:

1. Активный GitHub Issue целиком, включая зависимости и комментарии Codex.
2. `AGENTS.md`, `COLLABORATION.md`, этот файл и ближайший `AGENTS.md` изменяемого каталога.
3. `README.md`, `docs/IMPLEMENTATION_PLAN.md`, `docs/AUDIT-20261025.md`, `docs/CHECKLIST.md`.
4. Затрагиваемые исходники, тесты и `contracts/*`.

`docs/REMEDIATION_PLAN-20261025.md` — исторический архив, а не источник новой задачи или статуса. Источник конкретного scope и критериев — только активный Issue.

Приоритет требований: актуальное указание владельца → постоянные правила команды → активный Issue → CHECKLIST → IMPLEMENTATION_PLAN → код. Существенное противоречие или продуктовый выбор зафиксировать в Issue/PR и остановить расширение scope до решения Codex.

## 4. Архитектурные границы

- Использовать текущие Vue 3/TypeScript, Laravel, PostgreSQL, IndexedDB/WebCrypto и существующие stores/repositories.
- Matrix/Tuwunel — единственный backend переписки. Не добавлять Laravel-ленту, Chatify backend/auth/migrations или параллельные модели данных.
- Local-First & Optimistic UI: сначала защищённый локальный commit со стабильным idempotency key, затем сеть; учитывать offline/reload/retry/backoff, lost ACK, дубли, отмену, старые ответы и смену аккаунта.
- Не выдавать `Sent`, `Read`, `Uploaded`, `Deleted` или право доступа до подтверждения соответствующего источника истины.
- Не ослаблять E2EE, ACL, scopes, TTL, подписи и account/device isolation.
- Не помещать plaintext, ключи, recovery data и приватные metadata в URL, логи, аналитику, `localStorage`, fixtures или PR.
- Существующие данные сохранять совместимыми миграциями. Очистка хранилища и новое устройство вместо восстановления не являются исправлением.
- Новый UI должен работать на mobile/desktop, иметь RU/EN и не показывать внутренние Matrix/crypto состояния обычному пользователю.
- Фото, Photo Card, Note, Team, Assignment и Message остаются разными сущностями; ссылка или membership не расширяют права.

## 5. Размер задачи и WIP

- Один Issue — один проверяемый пользовательский результат — один Draft PR.
- Одновременно у Chatbot Agent только один Issue `In Progress`.
- Не начинать следующую задачу, не менять приоритет и не переписывать roadmap самостоятельно.
- Независимый найденный дефект записать в `Remaining`. Если он блокирует текущий Issue, указать точное условие и минимальный необходимый scope.
- Не добавлять посторонний refactor, новую инфраструктуру или зависимость без прямого требования Issue.

## 6. Работа с Issue и Project

1. Убедиться, что Issue имеет статус `Ready`, соответствует Definition of Ready из `COLLABORATION.md` и не имеет незакрытой зависимости.
2. Перевести Issue в `In Progress`, если права GitHub это позволяют; иначе написать короткий комментарий о начале работы.
3. Создать ветку от актуального `main` и Draft PR.
4. В первой строке PR указать `Closes #<issue-number>`.
5. После передачи PR перевести Issue в `Review`, если доступно; иначе оставить комментарий со ссылкой на PR.
6. Не закрывать Issue вручную и не переводить его в `Integrated`/`Accepted`.

Автоматическое изменение metadata допустимо; изменение кода `main`, merge и auto-merge — нет.

## 7. Содержимое PR

Заголовок: `[<Task ID>] <пользовательский результат>`.

Описание включает:

- `Closes #<number>`, Task ID, current/base/merge-base/head SHA и зависимости;
- поведение до/после, затронутые API/storage contracts и список файлов;
- миграции и обратную совместимость;
- offline/reload/retry/lost ACK/account switch/ACL/E2EE/TTL по scope задачи;
- реально выполненные проверки и отдельный список `NOT RUN`;
- ограничения, `Remaining` и короткий сценарий будущей mobile-приёмки.

Не писать `DONE`, `production-ready` или «проверено на устройстве» без факта. Итог передачи: `PR ready for local review`.

## 8. Review

Codex проверяет и при необходимости коммитит исправления в эту же ветку. Одновременный push двух агентов запрещён. После нового коммита повторяются только проверки затронутого риска. Chatbot Agent не создаёт второй PR для замечаний и не начинает новую задачу до следующего `Ready` Issue.
