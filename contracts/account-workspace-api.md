# Account workspace API — B03 local

2026-10-15. Prefix `/api/v1/identity/workspace`. Same Identity boundary/cookie/Origin/no-store rules as [Identity v1](identity-api.md). Authenticated requests are limited per confirmed account/device (180/minute); unauthenticated requests retain the IP bucket, challenges/proofs retain 30/minute/IP. The local gateway does not forward IP. Every workspace operation requires an authenticated account; client requests bind the expected account in the header, including multipart uploads and content reads. Prototype bearer codes do not authorize this API. Production/disabled Identity returns 404.

## Records, participants and Vaults

`GET /`: `{teams, tasks, presets, categories:{names,revision}, invitations}` for owned records and accepted memberships only. Private profile fields are not copied into people labels; an owner's explicit participant annotation is part of the team/task configuration. A pending invitation exposes the title, owner public ID, role/scope and expiry, not photo material. One personal Vault is created lazily. Assignment Vaults are distinct from team records.

`GET|PUT|DELETE /{kind}/{id}`, kind=`team|task|preset`, UUID id. Owner creates/edits/deletes; accepted members can GET team/task. PUT takes the current `revision` (0 for new), `name`, typed configuration and participants; DELETE takes `{revision}`. CAS conflict 409 preserves existing work. Unknown/foreign/deleted records return 404. Returned records include authoritative `id, revision, accountId, ownerPublicId, canManage, role, participants, discussion:{roomId,state}`. Server versions preserve capture context; client-provided owner/permission fields do not authorize anything.

Participant input: `{id:<PhotoBunker public ID>,name:<optional list label>,role:curator|contributor|viewer,photoScope?:default|none|thumbnails|all,notify?:boolean}`. Only accepted contacts or accepted people in the chosen team can be newly invited, never the owner themselves. `notify` is retained for UI compatibility; entry always creates a real invitation rather than silently granting access. Teams are permanent membership lists; their scope fields do not create photo grants. Existing accepted participants retain acceptance across explicit role/scope edits. Removed participants become revoked. Re-entry/expired or declined invitations receive a new ID and seven-day expiry.

`PATCH /invitations/{id} {accept:boolean}`: only the recipient, current record, unrevoked invitation; true requires unexpired invite and no bilateral block. Decline is allowed for expired invitations, and false can leave an accepted membership. Repeated current decision is idempotent. Acceptance updates only that record, not other teams/tasks/Matrix membership. Owner revision advances; every change remains visible to CAS.

Task configuration uses the U03 shape: instructions, start/end, count/checklist, optional team ID, frozen preset, contributor rules, completed state and participants. No team/preset is required. Start/end control capture availability and are separate from photo expiry. Accepted viewers cannot capture. Contributor defaults come from task rules; full contributor view is limited to their own files. Curator/viewer scopes may be narrowed. Assignment config edits and grant revocations do not reassign existing materials. Deleting a task removes other participants' access and schedules room reconciliation; owner materials remain until their own TTL/deletion.

`PUT /categories {revision,names}` stores a shared account list independently of camera presets. Preset payloads validate known rules/options; presets are configuration rather than grants. Local long/unlimited preset retention may remain configurable; the current cloud upload boundary accepts only 1 hour–14 days, with a visible failure and retained local capture otherwise. Paid entitlements remain B07.

## Account photographs

`POST /clock` returns `{id,issuedAt}` and persists an account-bound server anchor.

`POST /photos` is multipart: JSON `manifest` ≤50KB, `original` ≤64MiB, `preview` ≤2MiB, `thumbnail` ≤2MiB. The client creates a separate ≤80px thumbnail; preview is independent. Manifest includes UUID, capture dimensions/time/MIME/method, editable fields, optional assignment ID/task revision/profile, required original/preview/thumbnail SHA-256, retention anchor/seconds/expiry. Creator/account/Vault/grant bindings are server-owned. Assignment capture checks current accepted role, completion and dates; immutable context comes from a recorded task version. Category/checklist constraints use current assignment policy. Invalid transfer checksums do not reserve or confirm content.

Quota reservations serialize across an owner's Vaults, before object I/O. All three writes and HEAD sizes must succeed before the photo becomes active. Retry uses the same UUID and immutable fingerprint; different original/recipient bindings conflict. Failed writes remain discoverable pending rows. TTL is bounded by supplied expiry, server anchor, free maximum and assignment policy; deleted/expired IDs cannot resurrect. Local-copy import can preserve an older capture date while creating an explicitly new object, without extending an existing source deadline. Only an owner with an explicit account-bound import mapping may copy an archive into a closed task; unproven flags and other contributors cannot bypass capture dates/completion.

Upload result `{photo}` is complete only when the caller may view it. Upload-only receives a limited receipt with id/expiry/revision/upload status and grants, without image data/metadata. `GET /photos`: `{photos,deleted,receipts}`; upload-only receives only their own receipts and curator feedback. Revoked/foreign people do not receive those receipts.

`GET /photos/{id}` checks thumbnail permission and expiry. `GET /photos/{id}/original` requires full read; `/thumbnail` uses the 80px file for limited viewers and the independent larger preview for full readers. No public/presigned photo URL is returned. Limited DTOs omit GPS, description, tags, category/shot and profile data. Current technical context/author remains within accepted account scope. Every request rechecks ACL/TTL, including access from old encrypted messages.

`PATCH /photos/{id}` requires edit permission and a current revision; edits do not overwrite originals or silently extend expiry. TTL shortening is allowed; extension beyond existing expiry is rejected. Read-only/thumbnail-only scopes cannot mutate metadata. `DELETE /photos/{id}` checks delete permission, commits a tombstone first, then returns `{deletion:verified|pending}` (200/202). Cleanup removes original, preview and restricted thumbnail and strips the expired manifest; the tombstone remains.

`POST /photos/{id}/capture-metadata {revision,metadata}` is a narrow creator-only write in the 120 seconds after upload. It permits actual capture GPS samples/status, not arbitrary archive reads or replacement of capture time/camera/manual location. Current membership and TTL still apply. It returns only the new revision and enables late GPS without giving upload-only readers file access.

`POST /photos/{id}/review {revision,state,comment}`: owner/curator with edit/read rights, assignment photo only; accepted/correction/reshoot/rejected, comment required except accepted. `POST /photos/{id}/response {revision,comment}`: current creator, correction/reshoot only; upload-only can respond to feedback without reading images. Review revisions prevent overwriting another decision. Feedback is assignment domain data, not a second chat store.

Files remain a local plaintext prototype and manifests use APP_KEY at rest. This contract does not claim B04 image E2EE or issue decryption envelopes.

## Discussion and references

`GET|POST /assignments/{id}/discussion`: accepted assignment member/owner only; `{assignmentId,roomId,state}`. POST starts/retries durable reconciliation, 200 ready / 202 pending. Encryption/assignment binding is set on room creation; room-version-aware power levels are set before invitations; known aliases are verified before reuse. An unkeyed backend metadata device manages membership; SDK devices own E2EE. Source membership changes revoke photo grants first and mark the discussion pending. Scheduler/explicit retry handles partial failure; members do not receive original photo keys from this process.

`workspaceAccess.share` permits an internal reference; `shareExternal` separately permits file export. The contributor/viewer policy `participantsOnly` keeps internal discussion available while denying external export. Owner and curator retain their explicit sharing authority. This is an application policy, not prevention of copying pixels already granted for full viewing.

`POST /photos/{id}/reference`: share scope, active photo and current assignment access; ready bound room required. Returns `{photoId,assignmentId,roomId}`, with no file, token or storage URL. SDK encrypts the user-sent reference. The recipient's room membership never substitutes for photo ACL. Opening an expired/revoked ID is denied even if the message remains readable.

## Explicit migration

`POST /import-record {kind,source,value}` idempotently copies configuration into a new owned record, clears participants and requires real account invitations afterward. Source/target mapping is account-bound; originals are not changed. `POST /import-photo-id {source}` reserves an idempotent UUID for a client copy, returns `{id,committed}`; target tombstones deny reuse.

`GET /legacy` returns only configuration/photo IDs from legacy libraries already exclusively proven by this account. Existing `/identity/legacy-proof` requires the secret and records ownership; it never reassigns the library. `POST /legacy/photos/{id}/import {libraryId}` requires that proof, an active source, quotas and an unexpired target. It copies into distinct S3 keys, verifies sizes and returns `{id,originalPreserved:true}`. Unknown legacy authors stay unknown. A copied object does not exceed a known source deadline. Retry resumes pending copies and never recreates deleted target IDs.

Local imports preserve device originals/configuration and explicitly omit old textual participants from new grants. The UI binds source lists to the current account and cancels on account change. Partial failure preserves completed copies and remaining source data.


## B04 encrypted photo extension

For enrolled accounts new photos use `/api/v1/identity/secure/*`; legacy account photo POST/PATCH return 409. Legacy GET/DELETE still require a strong read token. Identity cookies alone permit encrypted capture transport, public context/key documents, clock and own submission receipts, not archive reads. A short-lived `X-PhotoBunker-Read` capability follows one-use `/secure/read/challenge` + signed `/secure/read/session`, bound to current Identity session/device/account/origin/key revision. Tokens are memory-only.

- `/secure/keys`, `/secure/device`, `/secure/context`, `/secure/plan`, `/secure/clock`: PB1-certified photo authority, certified capture device, owner-reviewed signed recipient plan and fixed TTL anchor.
- `/secure/photos` POST: five ciphertext files + canonical signed submission/packets. Validate signatures/current membership and plan, exact envelope recipients, framing/digests/bytes/anchor/quota. ACK only after all storage HEAD checks. GET/show/object GET require strong proof/current scope. Responses include serverTime and signed initial capture context; no plaintext photo metadata.
- `/secure/photos/{id}/objects` POST: signed CAS metadata/GPS/review/response object append; distinct producer permissions and replyTo binding. Idempotent replay returns the committed event revision. TTL may shorten, never extend.
- `/secure/pending/{id}` DELETE: strong proof + vaultId/assignmentId/expiresAt + current delete grant. Scoped cancellation works before row reservation; subsequent upload is 410. `/secure/photos/{id}` DELETE blocks reads first then verifies prefix cleanup.
- `/secure/links`: five-minute one-use new-device X25519 request, strong source approval, signed sealed response with PB4 and public trust/high-water state. Identity recovery/login precedes this flow.
- `/secure/migration`: strong source listing/content/mapping; `/{id}/verified` stores signed client readback attestation; DELETE requires explicit accepted confirmation, current target/source revisions and prior verification. Copy retains TTL and leaves source unchanged until cleanup.

Existing `/workspace/photos/{id}/reference` supports encrypted photos with strong proof, current share grant and an original envelope. It emits only photoId/assignmentId/roomId for Matrix encrypted discussion; no media or secret links. General workspace definitions retain B03 storage semantics. [Schemas and lifecycle](../docs/adr/0009-photo-e2ee-and-strong-unlock.md), [operations and limitations](../docs/operations/photo-protection.md).

## B05 — Immutable editor versions and isolated links

See [ADR 0011](../docs/adr/0011-encrypted-versions-and-private-links.md) and [operations](../docs/operations/editor-sharing.md). All owner routes are below `/api/v1/identity/secure`, require the current account-bound device session and photo read proof. No original or plaintext metadata is accepted.

- `GET /photos/{id}/versions`: current full-read grant, returns `{versions:[{id,event,signature,image:Packet,metadata:Packet,conflict}]}`. Only packets with a recipient envelope for the actor are listed. Thumbnail/upload-only and revoked memberships cannot list full edit documents.
- `POST /photos/{id}/versions`: edit grant, multipart `event`/`signature`/`packets` (`{image,metadata}`), `files[image]`, `files[metadata]`. The canonical signed `editor-version` event binds `{version:1,id,photoId,parent:<submission hash>,baseId:<observed version UUID|null>,imageHash,metadataHash}`. Kinds `local-version` and `version-metadata`, object revision 1, independently encrypted random object IDs, `initialHash=parent`. Validate B04 current plan/recipient list/device certificate, ciphertext hashes/framing, quota, parent state and TTL transactionally. Existing object IDs cannot be reused to overwrite originals. Exact retry returns the same version; changed payload under the same UUID is 409 (`version_id_conflict`). A stale base appends an immutable sibling with `conflict:true`, without changing original revision or any existing version. Per-photo locked ordinals determine the head even when timestamps tie. 403/404 permission, 410 deleted/expired, 413 quota, 422 malformed, 503 storage failure. Failed storage does not publish a version; ciphertext orphans are collected by the existing grace sweep.
- `GET /photos/{id}/shares`: current external-sharing grant, own issued share descriptors `{id,scope,versionId,expiresAt,revoked}`; expiry bounded by current parent TTL. No fragment key is retained server-side.
- `POST /photos/{id}/shares`: multipart `manifest` and `file` (independent ciphertext export). Manifest exactly `{version:1,id,scope:'view'|'download',versionId:UUID|null,expiresAt,iv:<12 byte base64url>,ciphertextHash:<BLAKE2b-256 base64url>,ciphertextBytes}`. Fresh AES-256-GCM key per export, 128-bit tag. AAD: UTF-8 `photobunker/share/v1\0` + canonical `{version,id,scope,versionId,expiresAt}`. Expiry must be future and ≤ parent expiry; selected version must belong to that photo. `file` max 64 MiB + tag, no plaintext filenames. Exact retry idempotent, revoked UUID cannot resurrect. Bytes count toward the owner's existing aggregate quota.
- `DELETE /photos/{id}/shares/{shareId}`: issuer or owner/curator; close access first, then verified deletion of isolated export. `{revoked:true,deletion:'verified'|'pending'}`, 200/202. Scheduler retries physical deletion; previous downloaded copies cannot be recalled.

Narrow public endpoints outside Identity (for external recipients only): `GET /api/v1/shares/{id}` returns the minimal manifest, `GET .../{id}/content` streams only that isolated ciphertext with `no-store`. Both validate parent state/TTL, share expiry/revoke and issuer's current shareExternal grant on every request; deny removed grants and expired objects with 410, unknown UUID 404. No cookies are needed, no original/author/assignment/preset/coordinates or edit layers are returned. Rate-limited coarse ephemeral bucket; no permanent S3 URL. Fragment secret never appears in an HTTP request. Scope `view` controls application download UI, not a promise to prevent extraction of pixels. `/s/{id}#<32-byte base64url key>` is the public viewer; every other app route remains account-only.

## R1-12 — Authenticated Protected Photo Browser collections

`PUT /browser/{uuid}` accepts `{assignmentIds:[uuid,...], expiresAt:milliseconds}`, 1–20 distinct assignments and at most 30 days. The browser UUID is generated and durably cached on the originating device before the request; replay of the **same** ID, ordered assignment IDs and expiry is idempotent. Any changed scope or expiry conflicts (409), expired/revoked IDs return 410. Creation requires current task owner or accepted curator for **every** assignment, independent of membership in a Team or Matrix room. There is no anonymous or public collection mode.

`GET /browser/{uuid}` responds `{id,assignments:[{id,name}],expiresAt,canRevoke}` only after confirming an active Identity session and current accepted membership in **every** listed assignment (with bilateral block and deletion checks). If any assignment is unauthorized, the response provides no partial list. Revoked/expired collection responds 410. The URL is **not a bearer capability** and does not add photo grants.

`DELETE /browser/{uuid}` is idempotent and restricted to its creator. It immediately revokes the collection route; it does not change pre-existing Workspace memberships or revoke a photo grant the viewer already has independently.

This API stores only an APP_KEY-encrypted array of assignment UUIDs, owner, expiry and revoke state; it never stores/copies photo originals, photo IDs, plaintext metadata, E2EE keys or previews. The authenticated client separately retrieves the current `GET /workspace/photos` or `GET /secure/photos` index with its existing individual per-photo ACL/TTL and cryptographic verification, intersects it with the allowed assignments, and projects only `id, assignmentId, permitted name, createdAt, expiresAt`. Full Photo Card navigation uses the existing independent `/gallery/{id}/card` authorization. Download/ZIP is outside R1-12.

The local Browser cache uses account+device+collection-scoped AES-GCM IndexedDB with a non-extractable CryptoKey, TTL check and in-memory PIN/photo-read gate. Only the **last server-verified minimal projection** is displayed offline; thumbnails and original bytes are not persisted in this cache. Online failure/403/404/410 never falls back to offline cache, and logout/account deletion purges the relevant encrypted rows. As with every offline-first cache, a remote revoke cannot be observed during an actual network outage; online revalidation is mandatory before any renewed remote material access.
