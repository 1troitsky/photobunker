# PhotoBunker — Functional & UX Audit Checklist

**Проект:** `1troitsky/photobunker`  
**Цель:** проверить, исправить и завершить перечисленные функции до production-ready качества.
**HiP** High Priority - задача с высоким приоритетом делается в первую очередь.
**LoP** Low Priority - задача с низким приоритетом делается в последнюю очередь.

## 0. Общие правила выполнения

Перед работой полностью изучить `AGENTS.md`, `README.md`, `docs/IMPLEMENTATION_PLAN.md`, `docs/AUDIT-20261025` и документацию соответствующих компонентов.

- [ ] Проверить существующую реализацию каждой функции, прежде чем писать новый код.
- [ ] Для каждого пункта определить статус: `DONE`, `PARTIAL`, `MISSING`, `BROKEN` или `BLOCKED`.
- [ ] Исправлять существующую реализацию вместо создания параллельных систем.
- [ ] Соблюдать Local-First & Optimistic UI: мгновенный отклик, локальное сохранение, фоновая синхронизация.
- [ ] Проверять offline, retry, reload, duplicate requests, account switching и права доступа.
- [ ] Не показывать пользователю успешное сохранение, отправку или удаление до соответствующего подтверждения.
- [ ] Сохранять существующую архитектуру E2EE для фотографий и Matrix для сообщений.
- [ ] Все функции должны иметь полноценный адаптивный UX/UI для мобильного PWA и desktop.
- [ ] Не считать задачу завершённой только на основании typecheck, сборки или unit tests.
- [ ] Не изменять `main`, не выполнять merge и не создавать PR без отдельного разрешения владельца.

**Первый блокер:** устранить ранее обнаруженную ошибку регистрации «Проверьте ключ восстановления». Убрать обязательный ручной ввод названия устройства, обеспечить восстановление после частично успешной регистрации и не блокировать создание профиля из-за временной недоступности Matrix.

## 1. Геолокация при запуске [HiP]

- [ ] При открытии приложения автоматически запускать определение координат, если пользователь ранее разрешил геолокацию.
- [ ] Если разрешение отсутствует, предложить включить геолокацию через понятный пользовательский сценарий.
- [ ] Хранить последнюю доступную координату, точность и время измерения.
- [ ] При открытии камеры немедленно использовать актуальные координаты, не начиная определение с нуля.
- [ ] При необходимости уточнять геометку уже сделанного снимка в допустимом временном окне.
- [ ] Не задерживать съёмку из-за GPS, если это не притиворечит заданию.
- [ ] Учитывать расход батареи, жизненный цикл PWA и ограничения фонового отслеживания.
- [ ] Позволять отключить отслеживание в настройках.

**Готово, когда:** пользователь открывает приложение, переходит к камере и сразу снимает фотографию с максимально актуальными доступными координатами. Если GPS недоступен, фото сохраняется без блокировки, но показывается сообщение, что у фото нет автоматических координат

## 2. Человекочитаемые NAME-ID фотографий [HiP]

**Формат:** `ABCD0001` — ровно четыре латинские буквы A–Z и четыре цифры.

- [ ] Каждая фотография получает постоянный человекочитаемый NAME-ID.
- [ ] NANE-ID автоматически становится названием фотографии по умолчанию.
- [ ] Название пользователь может изменить; Реальный ID остаётся неизменным.
- [ ] Четыре буквы могут быть уникальным префиксом задания или автоматически выделенным префиксом.
- [ ] В настройках задания добавить опцию **«Использовать ID задания для названий фотографий»**, включённую по умолчанию.
- [ ] Четырёхзначная часть последовательно увеличивается в пределах префикса: `ABCD0001`, `ABCD0002`, `ABCD0003`.
- [ ] Обеспечить отсутствие коллизий при одновременной работе нескольких участников и offline-съёмке.
- [ ] Обработать исчерпание диапазона 0001–9999 без изменения уже выданных ID.
- [ ] Использовать читаемые ID в карточках, галерее, сообщениях и названиях экспортируемых файлов.

**Важно:** внутренний UUID и публичный человекочитаемый ID — разные идентификаторы. Не переименовывать уже опубликованные фотографии при синхронизации.

Пользователь должен иметь возможность отправлять через сообщения:

- [ ] Задание.
- [ ] Личную фотографии из галереи телефона.
- [ ] Фотографиии из галереи PhotoBunker.
- [ ] Карточку фотографии вместо самого файла.
- [ ] Контакт и/или профиль пользователя.
- [ ] Текущую геолокацию — статический снимок.
- [ ] Live-геолокацию с выбранной продолжительностью и возможностью остановки.
- [ ] Пресет камеры.
- [ ] Приглашение в Team.
- [ ] Команду / ссылку на страницу Team.
- [ ] Заметку к фотографии или заданию.
- [ ] Обычные поддерживаемые файлы и документы.

### Требования

- [ ] Создать единый интерфейс выбора типа вложения.
- [ ] Внутренние объекты PhotoBunker отображать как интерактивные карточки внутри чата.
- [ ] При нажатии на карточку открывать соответствующий объект.
- [ ] Проверять права доступа получателя; отправка ссылки сама по себе не должна автоматически раскрывать закрытые данные.
- [ ] Для приглашений предусмотреть действия «Принять» / «Отклонить».
- [ ] Live-геолокацию передавать только по явному действию пользователя; после остановки или истечения TTL обновления прекращаются.
- [ ] Обеспечить понятную обработку offline и неуспешной отправки без потери вложения.
- [ ] Не дублировать содержимое сущностей, если достаточно защищённой ссылки на них.

**Готово, когда:** все перечисленные объекты можно выбрать, отправить, получить и открыть непосредственно из мессенджера.

## 8. Статусы заданий [LoP]

Использовать ровно пять основных статусов:

- [ ] `Waiting` — ожидает начала работы.
- [ ] `In progress` — работа выполняется.
- [ ] `Submitted` — результат отправлен на проверку.
- [ ] `Needs changes` — требуется доработка.
- [ ] `Completed` — работа принята и завершена.

### Проверки

- [ ] Заменить упрощённую модель `completed: boolean` полноценной моделью статусов.
- [ ] Настроить допустимые переходы и права участников.
- [ ] Позволить вернуть `Needs changes` в `In progress`, затем повторно отправить на проверку.
- [ ] Отображать статус в списке, карточке и подробной странице задания.
- [ ] Сохранять историю изменения статусов.
- [ ] Не путать статус задания со статусом проверки отдельной фотографии.
- [ ] Корректно обрабатывать конфликты при одновременном изменении статуса.

## 11. PIN-коды и удаление данных [HiP]

Все PIN-коды **необязательные** и включаются отдельно в настройках безопасности.

### 11.1. PIN входа в PhotoBunker 

- [ ] PIN для разблокировки приложения (не системный PIN телефона).
- [ ] Настройка допустимого количества ошибочных попыток.
- [ ] Настраиваемая задержка повторного ввода.
- [ ] Возможность блокировки доступа на выбранное количество часов.
- [ ] Опциональное удаление локальных данных после заданного числа ошибок — только при явном включении и подтверждении пользователем.
- [ ] Защита от перебора и корректное восстановление доступа владельцем.

### 11.2. PIN локального удаления

- [ ] Отдельный защитный PIN, запускающий очистку данных PhotoBunker на текущем устройстве.
- [ ] Перед очисткой проверить наличие подтверждённой актуальной облачной копии.
- [ ] Сохранить необходимые данные на сервере, если это разрешено пользователем и доступно соединение.
- [ ] Удалить локальные фотографии, ключи, кэши и относящиеся к аккаунту данные.
- [ ] Не удалять единственную копию ещё не синхронизированных данных под видом успешного резервного копирования.
- [ ] Обеспечить последующее восстановление разрешённых данных через штатный механизм аккаунта.

### 11.3. Экстренный PIN 

- [ ] Отдельный PIN для экстренного уничтожения доступа и удаления данных.
- [ ] Немедленно блокировать доступ к локальным данным и уничтожать доступные ключи.
- [ ] Запускать отзыв устройств, разрешений, внешних ссылок и серверное удаление.
- [ ] Предусмотреть сбои соединения и надёжную авторизацию запроса на удаление.
- [ ] Не показывать «удалено на сервере» без подтверждения сервера.
- [ ] Исключить случайное срабатывание при обычной ошибке ввода.
- [ ] Даже если сервер не отвечает и данные не получилось удалить - заблокировать вход в аккаунт и доступ к даннным сообщением 'Сбой программы'.

**Требование безопасности:** разработать и проверить отдельную модель угроз. Отличать удаление локальных ключей, удаление серверных объектов и копии, уже полученные другими пользователями. Не заявлять гарантированную физическую очистку OS или сервера там, где она технически не подтверждена.

- [ ] Показывать дату и время запланированного удаления фотографии.
- [ ] Показывать имя автора и ссылку на его профиль владельцу и уполномоченным участникам.
- [ ] Разрешить поделиться карточкой без передачи оригинального файла.

- [ ] Учитывать настройки личной фотографии или родительского задания/команды.

**Публичная функция** означает, что карточку можно намеренно опубликовать или отправить другому человеку, но сама фотография не становится публичной автоматически.

## 20. Обязательная проверка качества

Для каждой изменённой функции:

- [ ] Happy path — реальный пользователь проходит сценарий.
- [ ] Error path — понятная ошибка и возможность повторить действие.
- [ ] Offline / reconnect — корректная локальная работа, где это предусмотрено.
- [ ] Reload — данные и незавершённые операции не теряются.
- [ ] Account switch — отсутствие утечки данных между пользователями.
- [ ] Permissions — доступ проверяется на сервере и в E2EE-контексте.
- [ ] Expiration / revoke — истёкшие и отозванные ресурсы становятся недоступны.
- [ ] Mobile UX — корректная работа клавиатуры, touch, safe areas и PWA.
- [ ] Localization — русский и английский для новых пользовательских строк.
- [ ] Tests — целевые автоматические проверки обнаруженных дефектов.
- [ ] Manual acceptance — фактическая проверка владельцем, когда требуется реальное устройство или несколько аккаунтов.

## Важные замечания

Отдельно важны три принципа, которые я закрепил в задании:

Карточка ≠ фотография ≠ заметка. Это разные объекты с разными настройками видимости. Ссылка на карточку не должна автоматически давать доступ к оригиналу или личным заметкам.

Чат команды ≠ чат задания. Они создаются независимо и только по соответствующей настройке. Это позволит иметь одну постоянную переписку команды и отдельные обсуждения конкретных работ.

PIN не должен создавать ложное ощущение безопасности. Особенно при удалении данных: локальная очистка, сохранение серверной копии и безвозвратное удаление — три разных действия с разными гарантиями.

Чеклист можно использовать как единое техническое задание, но реализовывать лучше по отдельным, проверяемым этапам.
