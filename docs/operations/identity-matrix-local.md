# U04 / B01: аккаунт и локальный Matrix

Состояние на 15 октября 2026: рабочий локальный Identity API и управляемый Tuwunel. Это не готовый выпуск приватного сервиса. [B02: E2EE переписка, cross-signing и key backup](matrix-messaging.md) подключены; звонки остаются B06. [Решение](../adr/0006-identity-proof-and-matrix.md), [контракт API](../../contracts/identity-api.md).

## Запуск

После обычного `./scripts/dev setup` или `./scripts/dev up`:

```sh
./scripts/dev matrix
./scripts/dev api php artisan photobunker:identity-maintain --health
```

`matrix` добавляет случайные служебные секреты в игнорируемые `.env` и `apps/api/.env`, не печатает их, не меняет существующие значения и проверяет их согласованность. Затем применяет env_file к API/workers (при изменении настроек контейнеры пересоздаются с сохранением данных), запускает отдельный Compose profile, применяет добавочную миграцию Identity и проверяет Matrix client API. Старые таблицы и фотографии не удаляются. Если локальная конфигурация закеширована вручную, её надо обновить внутри контейнера API.

Основное приложение и камера запускаются без Matrix. `./scripts/dev down` останавливает также Matrix, сохраняя все volumes; после него `./scripts/dev up` и `./scripts/dev matrix` запускаются отдельно. Для очередного запуска уже подготовленного Matrix секреты не перевыпускаются.

Открыть «Профиль → Создать аккаунт». До регистрации клиент выдаёт ключ восстановления и требует подтвердить его сохранение. Email, телефон и имя не обязательны. Устройство получает отдельный закрытый ключ в IndexedDB. Анкета, контакты, запросы, блокировки и устройства работают с API. Раздел сообщений лениво проверяет подключение под тем же аккаунтом, без отдельного входа. Личные и групповые чаты с отдельным восстановлением истории доступны в B02.

## Проверенная совместимость

Образ: `ghcr.io/matrix-construct/tuwunel:v1.9.4@sha256:0e86c6164d6c9f5b60291938eb61ad8395021c37fe58d47a963ea7edddbedaec`.

`server_name = matrix.photobunker.test` выбран явно для разработки. Это постоянная часть MXID в данном volume. Для production требуется отдельное осознанное решение и отдельное окружение; замена имени в существующей базе не является миграцией.

| Операция | Реально проверенный API |
| --- | --- |
| Readiness | `GET /_matrix/client/versions` |
| Служебная регистрация | `GET/POST /_synapse/admin/v1/register`, nonce + shared-secret HMAC |
| Сервисный администратор | Отдельная регистрация с `admin=true`, до обычных аккаунтов |
| Пользователь | Регистрация с `admin=false`; `GET /_synapse/admin/v2/users/<mxid>` подтверждает имя и отсутствие admin-прав |
| Вход устройства | Backend `POST /_matrix/client/v3/login`, затем `GET /_matrix/client/v3/account/whoami` |
| Отзыв устройства | `DELETE /_synapse/admin/v2/users/<mxid>/devices/<device>`; прежний token получает 401 |
| Очистка точного QA fixture | `POST /_synapse/admin/v1/deactivate/<mxid>`, `erase=true` |

Административный PUT user из списка совместимости на закреплённом образе не прошёл проверку; adapter его не использует. На успешные логины действуют лимиты Tuwunel: повторные логины каждого запроса вызывали 429. Adapter кеширует Laravel-encrypted tokens на час, проверяет их через whoami и повторяет login после 401. Лимиты сервера не отключены. Служебные пароли и shared secret никогда не отправляются браузеру; обычный Matrix access token выдаётся только подтверждённому своему устройству и не записывается клиентом в постоянное хранилище.

Один UUID PhotoBunker даёт один детерминированный MXID. Повторный запрос и сбой между регистрацией и подтверждением не создают другую личность. Пароль Matrix хранится на backend зашифрованным APP_KEY; это credential входа, не ключ расшифровки сообщений. Отдельные подписи PhotoBunker также не заменяют Matrix crypto identity.

## Изоляция и частичные сбои

У Matrix нет опубликованных host-портов. Он находится в `matrix-internal` с `internal: true`, без федерации и публичной регистрации. Backend и gateway подключены к этой сети. Gateway проксирует client API; закрывает admin/federation/key routes и независимую Matrix регистрацию/login. Нет автоматического подключения к matrix.org. Access logs выключены. Это локальная конфигурация; production ingress, доверенный HTTPS и аудит остаются отдельной работой.

Регистрация PhotoBunker коммитится независимо от Matrix; состояние `pending` остаётся в PostgreSQL. Клиент запускает provisioning после входа, scheduler раз в минуту повторяет незавершённые операции. Команда `photobunker:identity-maintain` выполняет те же повторы вручную; `--diagnostics` печатает только безопасный этап/HTTP status/фиксированный Matrix errcode, без тел ответа, идентификаторов или credentials.

Отзыв сначала удаляет сессии PhotoBunker и блокирует дальнейший вход ключом устройства. Durable-флаг `matrix_revoke_pending` снимается лишь после подтверждения удаления Matrix-устройства. Пока Matrix недоступен, ранее выданный Matrix token ещё может действовать там: UI показывает ожидающий отзыв. После возвращения сервера повтор завершает удаление. Выход также закрывает все сессии текущего устройства и удаляет его Matrix-сессию, но оставляет право явного входа сохранённым ключом. После подтверждённого удаления сохраняется новый Matrix device epoch: следующая сессия не использует прежнюю crypto identity и восстанавливает историю её отдельным ключом. Незавершённый отзыв должен закончиться до новой Matrix-сессии; отзыв устройства требует нового подключения через recovery.

## Резервная копия и восстановление

Данные Tuwunel — отдельный volume `photobunker_matrix-data`. Копировать базу обычным файловым копированием следует только после остановки Matrix. Сохранить вместе с копией используемый образ/digest, TOML, тестовый `server_name` и закрытые секреты окружения в защищённом хранилище. Не класть их в Git, артефакты CI, общедоступный каталог или диагностический отчёт.

Для полного сохранения входа дополнительно необходимы PostgreSQL PhotoBunker и **тот же Laravel APP_KEY**, иначе нельзя расшифровать сопоставленные Matrix credentials и анкету. Конфигурация регистрации/admin должна соответствовать восстановленной базе Matrix. Пользовательский recovery kit восстанавливает вход PhotoBunker; он не заменяет серверный backup, Matrix secret storage и будущие ключи фотографий. Backup Gallery/S3/TTL и применение актуальных tombstones остаются отдельными процедурами.

Воспроизводимая компонентная проверка встроена в `check-account.mjs` для Chromium:

1. Создаёт только синтетические аккаунты с известными тесту ключами.
2. Останавливает Matrix, копирует volume read-only в новый одноразовый volume и запускает исходный сервер снова.
3. Поднимает из копии отдельный контейнер того же образа без host-портов в закрытой сети.
4. Через исходное сопоставление PostgreSQL/APP_KEY подтверждает существующий MXID и вход устройства в восстановленный Matrix.
5. Удаляет только созданный проверкой контейнер и копию volume, затем деактивирует точно известные QA-аккаунты и удаляет их записи приложения.

Это проверка восстановления компонента Matrix с действующей PostgreSQL, а не полный disaster recovery приложения, сообщений E2EE или S3. Клон после проверки не остаётся резервной копией.

## Проверки

При работающих локальных сервисах и установленных locked browser tools:

```sh
./scripts/dev check
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-account.mjs
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-ui-workspace.mjs
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-camera.mjs
```

В Linux/CI заменить путь браузеров на `/tmp/photobunker-playwright-browsers`. Account QA разрешён только для loopback origin, временно останавливает **только локальный Matrix** и возвращает его в `finally`. Использовать на локальном стенде без активной переписки. Recovery keys, пароли, tokens и тела запросов не печатаются и не снимаются на скриншоты.

Браузерные проверки включают создание/восстановление, сохранённый ключ устройства после reload и явный вход, видимость анкеты, contacts/accept/block, настоящий whoami, закрытые регистрацию/admin routes, отзыв PhotoBunker и Matrix. Дополнительно Chromium проверяет холодную копию, регистрацию и локальную съёмку во время сбоя, последующее provisioning и durable revoke. Физические телефоны остаются pending.

## Сохранение прежних данных

Локальные фото, задания и команды пока принадлежат прежнему пространству устройства/legacy library. Создание, смена или восстановление аккаунта не переносит их в его Vault и не выдаёт доступ другим людям. В Security можно явно доказать владение действующим legacy-кодом; сервер фиксирует исключительную claim и ничего не переприсваивает. Полный перенос с проверкой ACL и шифрованием — B03/B04. Контакт сам по себе не является участником команды, получателем фото или членом Matrix-комнаты.

`IDENTITY_DRILLS=0` отключает только повторение холодной копии и outage при работе над UI; обычный запуск и CI выполняют их. Последняя проверка экранов также подтвердила cross-tab logout и отсутствие горизонтального переполнения на 320/390/768/1440 px в Chromium/WebKit.
