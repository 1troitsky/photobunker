# B04 — защита фотографий

Актуальная модель: [один пользовательский ключ аккаунта](single-account-key.md), [ADR 0014](../adr/0014-single-account-key.md). Новые аккаунты настраивают фото автоматически; PB4 — внутренний материал, его не показывают и не требуют сохранять отдельно. Старый аккаунт подключает свой существующий ключ один раз. Утраченные прежние private keys требуют импорта старой копии; identity не сбрасывается.

## Пользовательский сценарий

1. Создать аккаунт и сохранить один ключ; фото и личная камера настраиваются автоматически.
2. Открывать фотографии на доверенном устройстве без повторного ввода ключа. Необязательный PIN защищает всё приложение.
3. Для общего задания проверить новых участников/отпечатки и права, если состав изменился. Это проверка получателей, не дополнительный recovery key.
4. После выхода или на другом устройстве войти тем же ключом аккаунта. Фото и счётчики скрыты до входа.

## Данные и права

В браузерном worker шифруются original, preview, отдельная миниатюра до 80 px, полные/ограниченные метаданные, GPS, review и response. Локальные версии редактора имеют отдельные шифрованные изображения и документы слоёв. Каждому объекту соответствует независимый DEK. Сервер хранит opaque IDs, размеры, сроки, ciphertext, подписанные контексты и sealed envelopes. Автор и первоначальный контекст съёмки проверяются отдельно от последующих правок. Review подписывает допущенный проверяющий, response — исполнитель; ответ привязан к конкретной ревизии review.

Upload-only не получает ключей оригинала или миниатюры архива. Thumbnail-only получает ключи только ограниченного изображения/метаданных. Текущие grants проверяются при чтении и перед завершением загрузки. Изменение права не выдаёт автоматически отсутствующие ключи уже снятого кадра. Отзыв ограничивает будущую выдачу; ранее полученные ключи/копии не отзываются.

Профиль аккаунта, общие определения пресетов, команды, контакты, политики заданий и служебные Matrix-данные остаются серверными operational data B03. Встроенный в кадр snapshot пресета/контекста зашифрован. Защита фотографий не означает E2EE всех справочников приложения.

## Очередь и срок

Новая очередь хранит только шифрованные byte buffers и публичный transport state в отдельной IndexedDB. Собственный pending-envelope позволяет восстановить недоставленный кадр после strong unlock; он никогда не отправляется серверу. После ACK удаляются pending-envelope и локальные ciphertext buffers всех пяти объектов. Поэтому после ACK архив читается с сервера; общий offline-кэш архива пока не реализован.

При изменении участников **Защита фотографий → Зашифрованная очередь → Обновить получателей** повторно запечатывает DEK, сохраняя original ciphertext, immutable encryption epoch, первоначальный anchor и deadline. До подтверждения актуального плана кадр остаётся в очереди. Late GPS — отдельный объект. Невысланные правки сохраняются зашифрованными и допускают повтор без молчаливой потери конфликта.

TTL облачного снимка 1 час–14 дней, ограничен anchor и политикой. Старый anchor может сократить оставшийся срок; reconnect/retry/rewrap не продлевают его. Текущий revoke/expiry блокирует доступ до физической очистки. Удаление недоставленного кадра создаёт scoped tombstone даже до первого upload, исключая позднее завершение загрузки. Scheduler очищает все объекты фото, sidecars и orphan prefixes, подтверждает удаление и повторяет сбои.

API-outage после холодной перезагрузки проверен при доступной оболочке разработки: приложение восстанавливает только публичную capture identity, требует совпадающий сохранённый device credential и подписанный план. Оно не открывает архив и не переключается на plaintext. Полная PWA работа без сети и физические телефоны требуют отдельной R01 проверки.

## Старые снимки

**Защита фотографий → Перенести старые фотографии** показывает локальные, собственные прежние account-кадры и исключительно доказанную legacy library. Создаётся новый encrypted ID; клиент заново скачивает, расшифровывает и сравнивает оригинальные байты, immutable metadata и локальные версии. Известный source TTL не продлевается; бессрочный источник получает максимум 14 дней новой облачной копии.

Удаление старого оригинала требует отдельного флага и повторной проверки. Удаляется только выбранный источник. Локальные реплики, другие устройства и недоставленные изменения сохраняются для отдельной проверки. Серверная cleanup-операция без клиентской verification attestation, текущей цели, совпадающей ревизии источника и явного подтверждения запрещена. Новые plaintext account uploads/правки после включения защиты запрещены. Старые адаптеры гостевого прототипа остаются для совместимости.

```sh
./scripts/dev check
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-photo-crypto.mjs
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-photo-workspace.mjs
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-photo-recovery.mjs
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/photobunker-playwright-browsers node tools/browser-spike/check-photo-offline.mjs
```

`PHOTO_BROWSERS=chromium` или `webkit` ограничивает engine. Linux CI использует `/tmp/photobunker-playwright-browsers`. Только синтетические accounts и fixtures; recovery keys, фото и токены не выводятся. Crypto tests используют настоящую libsodium, multi-frame/truncation/context/wrong-recipient cases и независимые PHP-native ciphertext/recovery vectors. API tests проверяют одноразовый read proof, актуальность плана, tamper, strong gate, delete-before-upload, expiry/replay и запрет неподтверждённой очистки.

Независимый security review, физические iPhone/Android, installed-PWA lifecycle, production HTTPS/CSP/memory review, полный disaster recovery с актуальными tombstones остаются release gates. B05 реализован локально: [облачные версии редактора, redaction и внешние ссылки](editor-sharing.md). Первый pin на свежей установке требует внешней проверки; key transparency нет. Замена PB4 не отзывает известный старый bundle/secret или ранее скачанные ключи, не заменяет compromised-authority reset. Очистка JS памяти best effort; компрометация origin/устройства и злонамеренный получатель вне гарантии. Повреждённый encrypted объект отклоняется; текущий клиент может потребовать повторного strong unlock после crypto failure.

Локальный результат проверки: 76 API tests / 986 assertions, 100 client tests, Pint 92 files, TypeScript/production build и private/signed S3 smoke. Все четыре B04 suites и U03 API-unavailable QA прошли в Chromium/WebKit; Chromium synthetic hardware pipeline — 3840×2160 с остановкой tracks. Сборка сохраняет предупреждение о больших SDK chunks; это не измерение мобильной памяти.

Повторная регрессия анкеты и полного B02 messaging/recovery прошла в обоих engines. При смене аккаунта приватные экраны пересоздаются; recovery-форма сохраняет введённый ключ во время начальной загрузки Identity. Если редактор анкеты пересоздан после session expiry, он возвращает в профиль с объяснением.

Наблюдение QA: один дополнительный WebKit-прогон базового сценария зарегистрировал `pageerror` при успешном upload/readback, без `window.error`/`unhandledrejection`. Повтор с расширенной безопасной диагностикой прошёл; новый тип события не включён в исключения монитора и остаётся наблюдением для R01. Уже известные нативные отмены index-poll учитываются отдельно; ошибки JS и неожиданные native events продолжают проваливать проверку. Это не основание объявлять мобильный lifecycle проверенным.
