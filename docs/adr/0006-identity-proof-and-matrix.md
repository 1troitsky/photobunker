# ADR 0006: Identity proof and managed Matrix (B01 local)

Date: 2026-10-15. Scope: local stand; E2EE and production release remain later stages.

Authentication uses P-256 signed, single-use, expiring server challenges, with a distinct account signing key and device signing keys. No email/password scaffold. The account private key is exported once as a high-entropy recovery kit and is never sent to the API. Device private keys are non-extractable WebCrypto CryptoKeys in a dedicated IndexedDB store. They are authentication keys, not future photo/Matrix encryption keys. Losing every device and the kit loses account access; support cannot reconstruct the key. This kit does not recover Matrix message history or future encrypted photos.

Challenges bind purpose, account/public key, device ID/public key and device name. The API verifies ECDSA through OpenSSL, translating WebCrypto P1363 signatures to DER; it does not implement cryptographic primitives. Consumption and account/device creation are transactional. Sessions use random HTTP-only SameSite=Strict cookies with server-side hashed tokens, bounded lifetimes and revocation. Mutating requests require the application header and an allowed exact Origin. Account registration retry is deduplicated by the root public-key fingerprint. Revoked devices cannot renew themselves; recovery requires a new device key or an explicit root-authorized enrollment.

Profiles default to private optional fields. Exact public-ID lookup reveals only fields allowed to the viewer. Contacts, requests and blocks are PhotoBunker relations; they do not create photo grants or Matrix room membership. Legacy library codes remain a separate local prototype credential. Account creation does not reassign old photos or import other libraries. Migration requires proof of the old library and an explicit plan in B03/B04.

Matrix uses official Tuwunel v1.9.4, pinned image, dedicated persistent volume, no federation and no public self-registration. Only the backend reaches the shared-secret registration/admin routes. A separate bootstrap service administrator is established before ordinary users. User MXIDs deterministically use account UUIDs; encrypted server-generated Matrix login passwords are transport credentials, not E2EE private keys. One PhotoBunker device maps to one Matrix device. Provisioning failures retain the account as pending and are retryable without creating a second MXID. Revocation denies PhotoBunker immediately and persists a retryable Matrix-device deletion intent until confirmed.

Local server_name is explicitly test-only and must never be used as the accidental production choice. API readiness and camera do not depend on Matrix readiness. No chat, key backup, cross-signing or call completion is claimed by B01. See the implementation runbook for actual tested endpoints, backup/restore and limitations.

Verified integration uses shared-secret registration, GET user, login/whoami and DELETE device on the pinned server, rather than relying on advertised PUT compatibility. Server token caches are encrypted, checked against whoami and scoped by homeserver URL; lock lifetimes cover bounded external calls. Profile edits bind both account UUID and revision; tabs invalidate stale identity state on logout. The cold Matrix-volume restore drill confirmed an existing account/device login using the original PostgreSQL/APP_KEY mapping and removed its disposable clone. Full-site/E2EE restore and independent security review remain pending.
