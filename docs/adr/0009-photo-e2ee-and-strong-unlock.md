# ADR 0009 — B04 photo encryption and strong unlock

2026-10-15. Local implementation decision and protocol review. Production release remains blocked on independent security review and physical mobile testing.

ADR 0002's libsodium secretstream framing, independent object DEKs, sealed-box recipients and immutable encryption epochs are retained. RFC 8785 canonicalization is provided by a pinned library. Public signed schemas contain ASCII field names, safe integer counters and base64url bytes; the PHP verifier rejects noncanonical encodings before verifying. Original, preview, restricted thumbnail, full metadata, restricted metadata, GPS, review, response and local editor versions are distinct objects/keys. Only ciphertext digests leave the client. A decoder verifies expected context, signature chain, envelope binding, ordered framing, FINAL, total length and ciphertext digest before releasing any plaintext.

B01 already deployed a P-256 account signing root. It remains the identity trust anchor rather than converting/reusing its secret as an encryption key. An explicit PB1 proof certifies an independent Ed25519 photo authority. That authority certifies independent X25519 recipient/pending keys, Ed25519 read-auth keys and non-extractable P-256 device capture-sign keys. Authentication keys do not decrypt photos. Private photo seeds live only in a dedicated worker and a recovery-encrypted bundle. PB4 is a separate random 256-bit photo recovery secret; PB1 and the Matrix history key do not restore photo decryption.

Read requests use a short-lived, device/Identity-session-bound read token obtained with a one-use read-key proof. Tokens and private read keys are never persisted. A cold device retains only public capture plans and non-extractable signing capability. PIN is a warm UI gate, never the wrapping key for persisted private keys. Reload/pagehide/explicit hard lock destroys the key worker. Visibility loss hides decoded private UI immediately; idle expiry is checked again before reuse. Memory clearing is best effort; origin compromise and OS copies remain outside this guarantee.

Shared Vaults use per-object envelopes rather than distributing one archive private key to every member. An owner-signed capture plan binds accepted people, their certified keys, read scopes, task revision, Vault and recipient epoch. Membership/policy/key changes invalidate the plan; an unlocked owner explicitly reviews and signs its replacement. Contributors receive only their own allowed object envelopes; thumbnail-only receives restricted image/metadata keys; upload-only receives none. Local own-pending envelopes never reach the server and are removed on confirmed submission. Rewrap preserves ciphertext/encryption epoch/deadline and requires strong unlock plus current submission authority. Previously downloaded keys/copies cannot be recalled.

First contact with another owner uses explicit TOFU/fingerprint confirmation; pinned identities and revision high-water marks reject substitution/rollback on that installation. A fresh device still needs an out-of-band fingerprint or trusted recovery/device linking to establish the initial pin. No key-transparency service is claimed. Server-controlled availability and rollback on a fresh installation remain limits. Signature authenticates the allowed producer, not physical scene/GPS/time truth.

New encrypted queues use a separate database from every plaintext prototype. Public rows contain only transport IDs, ciphertext, recipient envelopes, sizes, deadlines and retry state. Decrypted indexes/versions are not written into the plaintext databases. Existing plaintext originals remain readable only after explicit unlock and are migrated by a client copy, verified decrypt/readback and separately confirmed cleanup. The server never re-encrypts or derives previews. Migration cannot extend source TTL or resurrect a tombstone.

Team membership, task policy and Matrix metadata remain operational server-visible B03 data. Private capture context, embedded preset snapshots, descriptions, GPS, images and review comments are encrypted. Encrypting general team/contact directories is not inferred from photo E2EE. Matrix membership never grants photo keys; photo content is never sent to Matrix media.

Review findings resolved in this decision: sealed-box anonymity requires producer signatures; thumbnail and full metadata need different keys; pending recovery is local-only and acknowledged submissions must drop it; account-cookie auth alone cannot be a strong read capability; recipient epoch must not rewrite immutable file context; retry/rewrap must retain the original clock anchor/deadline; PIN hashes cannot wrap recovery seeds. Protocol/property/native-library vectors and negative integration checks are required before this stage is marked complete. This review is by the implementer, not an external audit.

Primary references: [secretstream](https://doc.libsodium.org/secret-key_cryptography/secretstream), [sealed boxes](https://doc.libsodium.org/public-key_cryptography/sealed_boxes), [KDF](https://doc.libsodium.org/key_derivation), [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785).

Implementation details: decoder framing is independently checked with PHP-native libsodium fixtures. Signed capture metadata revision 1 remains separate from later mutable overlays. Reviewer and contributor comments use distinct object kinds/signers. Local per-kind statement high-water marks, minimum observed deadlines and deletion markers reject known rollback; trusted device linking transfers these sealed, while plain PB4 recovery establishes new foreign pins explicitly. Legacy plaintext account writes are blocked after enrollment, including editor versions. Scoped cancel markers prevent uploads arriving after local deletion.

After upload acknowledgment local original/preview/thumbnail/metadata ciphertext buffers are discarded, alongside own-pending envelopes; archive reads require the API. Cold API-outage capture is supported with a cached public identity and matching persisted nonextractable credential, without restoring strong read. A full offline PWA archive is not claimed. PB4 replacement retains historical decrypt keys and a stable authority; compromised authority reset is a separate future operation. Operational account profiles and general preset definitions remain readable to the backend as well as task/team directories. See [B04 runbook](../operations/photo-protection.md).
