# Direct messenger and encrypted voice messages

Date: 2026-10-17

Messages open immediately from a profile or lookup, without a recipient acceptance screen. Matrix invitations remain an internal membership transport. An authenticated backend activation endpoint validates actual room state and joins recipients before the sender composes their first message. Contact lists are personal and synchronize between the owner's devices. The profile owner decides which people may see contact-only profile fields by adding them to their own contacts.

Voice recordings use MediaRecorder with runtime codec detection (WebM/Opus, MP4, Ogg). Press and hold records; release sends; slide left cancels; slide up locks. A tap or keyboard activation locks recording. Locked recording supports pause, stop/preview, cancel and send. Permission and send failures are visible; failed sends retain the draft in memory. Microphone tracks stop on completion, cancel, account change, app lock, background or unmount. Recordings are capped at ten minutes and 20 MiB.

Attachments use the existing Matrix Rust/WASM Attachment API, pinned to the SDK's 18.9.0 dependency. This implements [Matrix encrypted attachment v2](https://spec.matrix.org/latest/client-server-api/#extensions-to-mroommessage-msgtypes). Only ciphertext uploads to the authenticated local Matrix media repository. The file key, IV, SHA-256, duration, MIME type and waveform are inside the encrypted m.audio event. Decryption checks integrity before returning a playable Blob. Downloads require the current account's Matrix token, accept only its own homeserver's MXC IDs, and enforce the size cap even without Content-Length. Plain audio exists only in live browser memory and temporary object URLs, which are revoked on leaving, locking or deleting the message. No PB1, additional unlock code or plaintext media enters the API.

Playback provides pause, seek and 1/1.5/2× speed. Message redaction removes the playable event from synchronized timelines, including incoming messages where direct-chat permissions allow deletion for everyone. Redaction is not physical deletion of Matrix repository ciphertext or copies already held by recipients. Repository retention and physical cleanup must be handled as Matrix operations; photo-object deletion in Garage is a separate lifecycle. Physical mobile microphone permissions, codecs and background behavior require the device acceptance checks; browser-engine automation does not substitute for actual phones.

Cold recipient initialization can process a room key before the sender's device signatures arrive. Matrix SDK 44 removes unsigned/unknown-sender failures from its ordinary room-key retry queue. On SDK device/identity updates and chat opening, the app retries these events **only after SDK verification reports a valid owner signature**, through the same Rust decryptor and unchanged OnlySignedDevicesIsolationMode. Previously verified identity changes, truly unsigned devices, redactions and stale accounts are never granted trust by this retry. A targeted unit test covers these negative cases.

The gateway exposes only authenticated Matrix upload and client/v1 download, blocks legacy unauthenticated media downloads, and permits local Blob audio in CSP. Legacy media upload is needed by matrix-js-sdk 44; the gateway caps its body at 20 MiB and the homeserver checks the bearer token.
