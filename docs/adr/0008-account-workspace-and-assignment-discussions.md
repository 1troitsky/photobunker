# ADR 0008: Account workspace, photo grants and assignment discussions

Date: 2026-10-15. B03 local integration. Production guard and B04 photo encryption gates remain.

The existing Vue UI is retained. Account-authenticated `/api/v1/identity/workspace` endpoints own persistent teams, assignments, presets, common categories, invitations and photo Vaults. HttpOnly Identity sessions and expected-account headers authorize these endpoints; no prototype bearer code becomes an account credential. Legacy API and local records remain separate and intact. One personal Vault is created lazily under an account lock; each assignment owns a separate Vault. No setup wizard/team/preset is required for personal capture.

Team membership, assignment membership, Vault grants and Matrix room membership are independent. A team supplies an editable participant snapshot to a new assignment. Adding somebody sends an account-bound invitation, not a grant; acceptance is explicit and expires after seven days. Role/scope changes use owner revision checks. Removing a participant revokes PhotoBunker access immediately. Team edits and leaving a team do not change an independent accepted assignment. Re-entry after rejection/revocation uses a new invitation. Contacts/accepted team members can be invited; arbitrary textual IDs cannot create privileges.

Owners manage their records and materials. Curators can read/edit/review authorized material; contributors upload and, when allowed, see only their own photos; viewers cannot upload/edit/delete. `photoScope` narrows the defaults to none, thumbnails or full view. Contributor full view is still limited to their own submissions. `thumbnail-only` means a separate image object capped by the client at 80 px, not CSS hiding. Full previews and originals are distinct objects and are denied by every content endpoint when the caller lacks full read access. Limited viewers receive no GPS, description, tags or profile payload. Already received plaintext/copies cannot be recalled.

New photos use separate workspace tables and S3 object keys. Reservation/owner-level quota serialization happens before object I/O; three objects are written and HEAD-sized before active confirmation. Originals are immutable, editable data uses optimistic revisions, deadlines are bounded by account clock anchors and the local free maximum of 14 days, and committed tombstones deny access before cleanup. Metadata-only capture sidecars are permitted for the current creator in a short post-upload window without granting archive reads. Curator feedback and contributor replies are assignment domain data, separate from chat events.

This stage deliberately connects the authorized local plaintext prototype. Workspace definitions/manifests are encrypted at rest with Laravel APP_KEY, so the backend can read them. Image objects are not yet client-encrypted. Rust E2EE protects Matrix messages; it does not make the new image store E2EE. B04 introduces signed recipient bindings, encrypted media/envelopes and strong unlock. B03 has no photo decryption keys to give upload-only contributors. No release is authorized by these changes.

An assignment discussion is a private Megolm room. Laravel manages only room metadata and membership using a backend-only `PB_WORKSPACE` device on the owner's MXID; that device never publishes E2EE device keys, stores signing/room keys, sends chat events or uploads media. SDK devices retain all message encryption/decryption. The backend generates no second visible login. Initial room state binds assignment ID and encryption/history policy. Power-level policy is installed before inviting other users. Room version 12 gives the creator implicit power and forbids listing that creator in `users`; older supported versions use an explicit owner entry. Empty map fields remain JSON objects through the PHP adapter. A deterministic alias locates a room after an interrupted creation; its owner/binding/encryption are checked before recording it. Membership invitations/kicks reconcile from accepted assignment participants, with durable pending state, retry and revision checks. Partial Matrix failure does not roll back photo permissions. The UI reports the partial state. Membership metadata/title remains visible to Matrix.

Photo references are user-sent encrypted Matrix text events containing only the PhotoBunker ID/assignment ID, never original files, tokens or public storage URLs. The sender's reference endpoint checks current scope and TTL; every recipient opening the ID goes through fresh PhotoBunker authorization. Membership in the room does not authorize a photo. Old messages cannot bypass expiry/revoke. Removing someone from a room cannot erase previously delivered message keys or ciphertext.

Migration is explicit copy/import with idempotent mappings. Device records and proven legacy libraries are not reassigned. Local/legacy team and assignment configuration is copied with participants cleared; users must assign real contacts again. Original records retain the old participant descriptions. Preset snapshots are retained, and old server photo authors are marked unknown rather than attributed to the new account. Server legacy reads require the existing exclusive ownership proof; copied files get distinct object keys and cannot exceed a source deadline. Expired/deleted sources and target tombstones do not resurrect. A partial copy can retry without duplicating completed work. No old key/code is printed or placed into a Matrix message.

Client state and local photo/editor storage are bound to account ID. Account switches close old private forms and stop old requests from mutating the next account. Existing device-only workflows remain usable without Identity/Matrix. SDK import/one-owner Rust store/history recovery remains B02. Cold offline shared archive access is not promised; capture can queue locally, but current server grants decide eventual submission and retrieval.

Protocol references: [Matrix room membership](https://spec.matrix.org/v1.15/client-server-api/#room-membership), [room creation](https://spec.matrix.org/v1.15/client-server-api/#creation), [room version 12 creator rules](https://spec.matrix.org/latest/rooms/v12/), [SDK](https://matrix-org.github.io/matrix-js-sdk/index.html). Real compatibility and negative-path evidence are recorded in the B03 runbook after validation.
