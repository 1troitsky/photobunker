## 1. Что представляет собой PhotoBunker

PhotoBunker — локально-ориентированное PWA для приватной съёмки, хранения, обработки и передачи фотографий, совместных заданий и защищённого общения.

Главные пользовательские сущности:

- **Аккаунт** — постоянная личность без обязательных телефона и email.
- **Контакт** — человек, которому можно написать, позвонить или назначить роль.
- **Пресет камеры** — повторно используемые правила съёмки и обработки.
- **Команда** — постоянный набор участников и ролей.
- **Задание** — конкретная работа с инструкциями, участниками, сроком и списком кадров.
- **Фотография** — неизменяемый оригинал, метаданные, версии, права и срок хранения.
- **Переписка** — личная или групповая Matrix-комната с E2EE, вложениями и локальной очередью.

Основная навигация: **Задания, Сообщения, Камера, Фото, Профиль**.

## 2. Непереговорные требования к UX

### Local-First и Optimistic UI

Интерфейс не ждёт сервер, если действие можно безопасно зафиксировать локально.

1. Действие пользователя сразу отражается в UI.
2. Операция получает стабильный локальный `operationId` и сохраняется до сетевого запроса.
3. Серверный или Matrix ID заменяет временный ID без второго элемента в интерфейсе.
4. Потерянный ответ, повтор запроса и reconnect не создают дубликаты.
5. Ошибка показывает понятные Retry/Cancel или мягкий rollback, не уничтожая введённые данные.
6. Медленный ответ старого аккаунта, экрана или комнаты не может изменить текущий экран.
7. Отмена, смена аккаунта и уход со страницы прекращают или изолируют устаревшие запросы.
8. Retry использует bounded exponential backoff и тот же idempotency key.
9. Offline-состояние является обычным режимом, а не пустым или заблокированным экраном.
10. Нельзя показывать `Sent`, `Delivered`, `Read`, `Uploaded` или `Deleted`, пока соответствующий источник истины этого не подтвердил.

### Локальное хранение

- App shell и разрешённые локальные данные должны открываться без сети.
- Очереди сообщений и фотографий хранятся в IndexedDB в зашифрованном виде.
- Plaintext сообщений, закрытых метаданных и ключей нельзя переносить в `localStorage`, аналитику или серверный поиск.
- Локальный commit и облачное подтверждение — разные состояния.
- Смена аккаунта, выход и отзыв устройства очищают относящееся к прежнему аккаунту состояние, listeners, blob URLs и callbacks.

### Человеческий интерфейс

- Обычный пользовательский путь не должен показывать внутренние этапы Matrix, recovery, provisioning и миграций.
- Восстановление старой истории не блокирует создание комнаты и отправку новых сообщений.
- Ошибки не должны маскироваться бесконечными «Подключаем…» или «Открываем…».
- На desktop используется двухпанельная переписка, на телефоне — один полноэкранный поток с вводом над safe area.
- Кнопки, диалоги, аватары и пустые состояния должны оставаться пригодными на 320–1440 px.

## 3. Действующая архитектура

| Область | Текущее решение |
| --- | --- |
| Web | Vue 3, TypeScript, Vite, PWA |
| API | Laravel, PostgreSQL, worker/scheduler |
| Локальная разработка | Docker Compose/OrbStack, `http://localhost:8080` |
| Объектное хранилище | private S3-compatible Garage |
| Identity | аккаунт PhotoBunker, публичный ID, device session, proof-of-possession |
| Сообщения | Matrix/Tuwunel, matrix-js-sdk, Rust crypto/WASM, E2EE |
| Звонки | MatrixRTC + LiveKit; Safari/mobile ещё не приняты |
| Локальные очереди | IndexedDB, AES-GCM wrapping, стабильные transaction IDs |
| Фото | client-side encryption, отдельные original/preview/thumbnail/version objects |

PhotoBunker не создаёт вторую Laravel-таблицу сообщений. Matrix остаётся источником истины для комнат, событий, E2EE и receipts. Laravel отвечает за Identity, участников PhotoBunker, фотографии, задания, права, TTL и связующие операции.

Chatify v2 используется как источник UI/UX-паттернов, а не как backend, auth или криптографический слой. Нельзя устанавливать его destructive migrations, integer user model или attachment backend. Целевой общий UI и typed adapter boundary описаны в `docs/references/artefacts-messages/`; Artefacts-специфичные backend/gate требования к PhotoBunker не применяются.

### Текущий статус переписки

23 октября исправлены вход в личный диалог, отображение composer, создание/активация комнаты, привязка durable outbox к возвращённому `roomId`, повторная отправка после reload и блокирующий `beforeunload`. Технически накопленная очередь дошла до Matrix как зашифрованные события.

Это **не означает пользовательскую приёмку**. Переписка считается рабочей только после того, как владелец на текущем `localhost:8080` вручную выполнит обмен между двумя аккаунтами и увидит сообщения у обоих участников.

## 5. Приоритетный roadmap

### P0 — принять базовую переписку

Никакие новые функции мессенджера не важнее этого этапа.

Обязательный ручной сценарий:

1. Открыть контакт из списка, профиля и задания.
2. Нажать «Написать» и сразу увидеть нормальный экран диалога с полем ввода.
3. Ввести текст и мгновенно увидеть один optimistic bubble.
4. Убедиться, что диалог появился слева без перезагрузки.
5. Получить сообщение во втором аккаунте и ответить.
6. Проверить `Sending → Sent → Read` только по фактическим Matrix-событиям.
7. Отключить сеть, отправить два сообщения, перезагрузить приложение, включить сеть и получить ровно два сообщения без дублей.
8. Повторить отправку после временной ошибки, не теряя текст.
9. Убедиться, что recovery старой истории не блокирует новые сообщения и не висит баннером в обычном чате.
10. Проверить desktop и узкий mobile viewport.

Критерий завершения: владелец проходит сценарий вручную. После этого выполняются только целевые regression-тесты send/outbox/reconnect/account switch; широкая матрица запускается перед релизным этапом.

### P1 — единый Local-First слой приложения

- Унифицировать модель локальной операции для сообщений, заданий, контактов, фото и настроек.
- Явно разделить `local`, `syncing`, `confirmed`, `failed`, `conflict`, `cancelled`.
- Сохранять разрешённое состояние в IndexedDB с account/device scope.
- Добавить version/revision checks, cancellation и ignore-stale-response.
- Устранить интерфейсы, которые остаются пустыми при недоступном API.
- Обеспечить мгновенный offline-start для ранее открывавшихся данных.

### P2 — задания, команды и контакты как единый сценарий

- Контакты доступны при выборе участников без ручного повторного ввода ID.
- Команда и участники задания имеют понятные роли и доступы.
- Создание задания оптимистично появляется в списке и переживает offline/reload.
- Обсуждение задания открывает реальную E2EE-комнату без отдельной настройки.
- Ссылка на фото в сообщении не расширяет photo ACL.
- Revoke и block немедленно отражаются локально и проверяются сервером при синхронизации.

### P3 — завершить фото-сценарий

- Съёмка не ждёт сеть, GPS или сервер.
- Локальный encrypted commit предшествует сообщению «Сохранено».
- Upload/finalize идемпотентны; поздний ACK не воскрешает удалённый или истёкший снимок.
- Оригинал неизменяем; редактор создаёт отдельные версии.
- Privacy mask запекается в выдаваемый файл; оригинал и слои не попадают получателю.
- TTL ограничивает original, previews, versions и shares.
- Проверить восстановление очереди, storage full, kill mid-write и серию кадров на физических устройствах.

### P4 — безопасность и восстановление без помех UX

- Один понятный ключ аккаунта и отдельное объяснение возможностей recovery.
- Новый подтверждённый device восстанавливает разрешённую историю и фото.
- Неподтверждённый device может отправлять новые E2EE-сообщения; недоступная старая история показывается только внутри соответствующего потока или раздела безопасности.
- Logout/revoke удаляют device session, локальные keys, decrypted previews и scoped queues.
- Проверить block, membership, photo grants и Matrix room powers независимо.
- Провести отдельный security review до публичных обещаний E2EE/удаления.

### P5 — расширенный мессенджер и звонки

Только после P0:

- вложения и encrypted media;
- голосовые сообщения;
- reply/edit/reactions/pin/search/folders/archive/delete semantics;
- групповые комнаты и moderation powers;
- честные receipts, typing/presence и privacy controls;
- MatrixRTC/LiveKit на Chromium, Safari, iPhone/Android и через TURN/NAT.

Функция показывается только если adapter capability реально доступна. Нельзя имитировать server search для E2EE, delivered/read или background incoming calls.

### P6 — mobile и эксплуатационная готовность

- Установка и запуск PWA на реальных iPhone и Android.
- Camera permissions, keyboard, safe areas, background/foreground, low memory и storage eviction.
- Offline/API/DB/S3/Matrix/LiveKit failure drills.
- Backup/restore PostgreSQL, Garage и Tuwunel без resurrection удалённых данных.
- Accessibility, RU/EN, CSP, dependency review и измеренные performance limits.
- Production config, monitoring без plaintext и понятные runbooks.

### P7 — ёмкость, тарифы и разовые платежи

- Capacity/TTL accounting учитывает originals, previews и versions.
- Free срок не превышает 14 дней; платные варианты задаются конфигурацией.
- Только разовая предоплата, без скрытой автоматической подписки.
- Immutable invoice/credit ledger и идемпотентное начисление.
- Реальные деньги включаются отдельным решением владельца после стабилизации продукта.

## 6. Порядок приёмки изменений

1. Реализовать цельный пользовательский путь.
2. Codex проверяет его локально, включая целевую браузерную диагностику.
3. Исправить найденные блокеры без расширения scope.
4. Добавить короткие целевые проверки на обнаруженные race/failure cases и интегрировать в пределах разрешения владельца.
5. Перед релизным этапом выполнить широкую регрессию и security matrix; ручную mobile-приёмку владельца провести после удалённого развёртывания.

Количество тестов, успешная сборка и synthetic browser automation не заменяют ручную приёмку. Они подтверждают только заявленную техническую область.

## 7. Definition of Done

Задача завершена, если одновременно выполнены условия:

- пользовательский сценарий доступен из обычной навигации;
- happy path пройден владельцем вручную;
- offline/retry/cancel/account-switch не теряют и не дублируют данные;
- UI не ждёт сеть без необходимости и не показывает ложный успех;
- права проверяются источником истины, а не только скрытием кнопки;
- сохранённые данные изолированы по аккаунту и устройству;
- нет нового plaintext в логах, browser storage или URL;
- ошибки имеют понятное действие, а не бесконечный spinner;
- typecheck/build проходят для изменённой области;
- незавершённые ограничения явно перечислены без заявления «готово».
