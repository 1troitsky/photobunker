## 2. Текущий блокер и порядок

Исходный блокер: владелец не мог войти и пройти переписку. До восстановления входа нельзя было принять камеру, переписку или остальные функции. Аудит зафиксировал две опасные связи, исправленные в R0-01/02:

- `AccountAuthView.vue` ожидает `ensureAccountPhotos()` и `ensureNewAccountMessaging()` до перехода в приложение; многие `identity.*` и `DOMException` сводятся к ошибке ключа.
- `router.ts` ожидает сетевой `loadIdentity()` в guard. Это требует проверки при медленном API; точная причина текущего отказа входа пока не воспроизведена.

Приоритеты:

1. **R0:** регистрация/вход, затем реальный текстовый обмен двух аккаунтов.
2. **R1:** задачи HiP из CHECKLIST с учётом зависимостей, затем связанные пункты без метки.
3. **R2:** прочие пункты без метки, не закрытые в R1.
4. **R3:** LoP только после предыдущих этапов. Узкая часть LoP может быть зависимостью HiP; это фиксируется в карточке, а не переносит весь LoP вперёд.
5. **R4:** итоговая эксплуатационная, mobile и security-приёмка.

Чеклист содержит и тематический порядок P0–P6, и метки HiP/LoP. Здесь HiP получает приоритет после блокеров. Пять статусов заданий, будущие языки, звонки, аватары и геогруппировка остаются LoP. Наличие карты в Photo Card (HiP) не требует досрочно реализовывать геогруппировку (LoP).

## 3. Разделение работы

| Участник | Ответственность |
| --- | --- |
| Владелец | требования, продуктовые решения, разрешение merge; ручная приёмка на телефоне после завершения работ и удалённого развёртывания |
| Chatbot Agent | код в отдельной ветке и PR по выданной карточке; честный список недоступных проверок |
| Codex | подготовка карточек, review, локальный запуск и диагностика, доработка PR, передача владельцу и ведение статусов |

Chatbot Agent не изменяет `origin/main`/`main` никаким способом и не делает merge. Codex интегрирует проверенные изменения в пределах разрешения владельца. 25 октября владелец разрешил интеграцию готовой R0-01 и выдачу следующего задания, отдельно перенёс все свои ручные проверки на телефон после удалённого развёртывания. Одновременно один агент пишет в конкретную PR-ветку; право изменения передаётся явно. Новый PR начинается после завершения зависимости, если иное не согласовано.

Цикл реализации задачи: `очередь → выдана → PR → локальная проверка/доработка → разрешённая интеграция → технически завершена`. Финальная ручная приёмка владельца на телефоне проходит после удалённого развёртывания и фиксируется отдельно.

`DONE/PARTIAL/MISSING/BROKEN/BLOCKED` описывают функцию по CHECKLIST; этап передачи PR и техническое завершение пакета хранятся отдельно. `PR создан`, `build passed` и `merged` сами по себе не означают DONE. Технически завершённый пакет имеет PR/head SHA, фактические целевые проверки и подтверждённый локальный пользовательский путь. Пункты финальной mobile/production-приёмки остаются открытыми до проверки владельца. Если PR изменился после проверки, затронутое поведение проверяется заново.

## 4. Общие критерии для каждой задачи

- Сначала изучить существующую реализацию и воспроизвести дефект в пределах задачи.
- Исправить пользовательский путь через UI, persistence, API/transport и обработку ошибок, не создавая вторую систему.
- Мгновенная реакция UI отделена от локального commit и подтверждения сервера. Окончательные права, ключи, TTL, отправка и удаление не подтверждаются фиктивно.
- Учитывать offline/reload/retry/backoff, потерянный ACK, временные ID, отмену, старые async-ответы, account switch и несколько вкладок по риску изменения.
- Не сохранять приватный plaintext/ключи в логи, URL, `localStorage`, публичные caches или отчёты.
- Серверные ACL, E2EE, scope и TTL остаются обязательны. Ссылка, room membership и local cache не дают новых прав.
- Сохранять данные владельца; не очищать IndexedDB/volumes и не регистрировать новые устройства вместо восстановления операции.
- Новые UI-строки RU/EN, mobile/desktop, понятные error/retry и отсутствие бесконечных блокировок.
- Codex выполняет typecheck, узкую браузерную диагностику и целевые регрессии изменённого пути. Промежуточную ручную проверку владельца не требовать. Полные матрицы выполняются по конкретному риску и перед релизом.
- CHECKLIST §20 — обязательные проверки изменённой области; §21 — формат фактического отчёта в PR.

## 6. Решения до соответствующей реализации

Решения фиксируются в этом разделе/карточке задачи и PR, без отдельного нового ADR. Подготовка варианта — работа исполнителя; продуктовый компромисс подтверждает владелец.

- **D1 / NAME-ID:** четыре буквы + 0001–9999, глобальная область уникальности/assignment prefix, reservation для offline, multi-device и exhaustion. Внутренний UUID неизменен; опубликованный code не перенумеровывается. При независимых offline-клиентах без заранее выданных непересекающихся диапазонов одновременно обещать последовательный постоянный общий code нельзя. Нужны правила для исчерпанного резерва без блокировки безопасной съёмки; не принимать временный code за постоянный молча.
- **D2 / Presence:** проверить Tuwunel/Matrix capabilities и серверную фильтрацию all/contacts/nobody. Если Matrix не обеспечивает требуемую приватность, сначала предложить способ ограничить выдачу. Одного скрытия в Vue недостаточно. Определить интервалы «недавно/давно» и поведение нескольких устройств.
- **D3 / PIN и удаление:** подготовить threat model, классификацию ключей/кэшей и проверку облачной копии. Порядок: подготовка узкого долговечного авторизованного delete intent → уничтожение локального доступа → доставка/подтверждение серверной очистки.
