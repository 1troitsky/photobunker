# PhotoBunker — совместная работа владельца, Codex и Chatbot Agent

Этот документ задаёт постоянный рабочий цикл команды. Технические требования проекта находятся в `docs/IMPLEMENTATION_PLAN.md`, правила Chatbot Agent — в `CHATBOT-AGENTS.md`, текущая очередь исправлений — в `docs/REMEDIATION_PLAN-20261025.md`.

## 1. Участники и ответственность

### Владелец

- Определяет продуктовые требования и приоритеты.
- Передаёт Chatbot Agent подготовленное Codex задание.
- Получает от Chatbot Agent ссылку на PR и передаёт её Codex.
- Выполняет ручную приёмку на телефоне после завершения работ и развёртывания на удалённом сервере.

Владелец не обязан запускать локальные команды, разбирать ветки или тестировать каждый промежуточный PR.

### Codex

- Читает roadmap, текущую очередь, код и результаты предыдущей задачи.
- Готовит владельцу полностью готовое задание для Chatbot Agent и всегда напоминает ему сначала прочитать `CHATBOT-AGENTS.md`.
- После получения PR проверяет diff и архитектурные границы, воспроизводит затронутый сценарий, запускает только необходимые локальные проверки и устраняет найденные дефекты в той же PR-ветке.
- Сливает проверенный вариант в `main`, синхронизирует локальный `main` и обновляет единую очередь задач.
- Сразу после интеграции сообщает статус завершённой задачи и выдаёт владельцу следующее готовое задание для Chatbot Agent.
- Не перекладывает на владельца техническую диагностику и не задерживает пользовательский сценарий широкими тестовыми матрицами без конкретного риска.

### Chatbot Agent

- Не имеет доступа к локальным файлам, локальным сервисам, браузеру владельца и сложным локальным проверкам.
- Перед началом каждого задания читает в GitHub `CHATBOT-AGENTS.md`, корневой `AGENTS.md`, этот документ и указанные в карточке материалы.
- Реализует только полученную карточку в отдельной ветке `chatbot/<task-id>-<name>` и создаёт Draft PR в `main`.
- Никогда не изменяет и не сливает `main`, не включает auto-merge и не начинает следующую задачу самостоятельно.
- Возвращает владельцу URL PR, base SHA, head SHA, перечень изменений и честный список выполненных и недоступных проверок.

## 2. Источники задач

Продуктовый roadmap — раздел **«Приоритетный roadmap»** в `docs/IMPLEMENTATION_PLAN.md`. Конкретная последовательность исполнимых карточек и зависимости находятся в `docs/REMEDIATION_PLAN-20261025.md`.

Каждое задание Chatbot Agent должно:

1. Иметь один основной Task ID из текущей очереди.
2. Указывать конкретный пункт и результат продуктового roadmap, которому оно соответствует.
3. Давать один проверяемый пользовательский результат, а не произвольный набор файлов или тестов.
4. Описывать зависимости, границы, offline/reload/retry/account switch, права, E2EE и TTL в применимой части.

Если пункт слишком большой для безопасного review, Codex делит его на последовательные части с суффиксами, например `R1-03A`, `R1-03B`. Каждая часть заканчивается работающим проверяемым состоянием и отдельным PR. Если несколько соседних шагов слишком малы, их можно объединить в одной карточке только когда они образуют один пользовательский сценарий и перечислены в задании по отдельности. Нельзя смешивать несвязанные пункты roadmap ради размера PR.

## 3. Обязательное обновление main в контексте Chatbot Agent

Chatbot Agent не должен полагаться на сохранённую в памяти копию репозитория, прошлую переписку, старый diff или ранее увиденный SHA. Перед чтением исходников и любым изменением кода он обязан заново получить актуальное состояние ветки `main` из GitHub и считать его единственным источником текущего кода и документов.

Порядок обязателен:

1. В начале каждого задания заново открыть `main`, получить его текущий head SHA и сверить его с `Base` в карточке.
2. Сбросить устаревший мысленный/кэшированный контекст файлов и повторно прочитать с актуального `main` как минимум `AGENTS.md`, `COLLABORATION.md`, `CHATBOT-AGENTS.md`, карточку задачи и все затрагиваемые исходники. Нельзя писать код по содержимому файлов, запомненному в предыдущем задании.
3. Если указанный в карточке SHA уже не является head `main`, сначала сравнить изменения. Создавать рабочую ветку от текущего `main`; в PR указать полученный фактический base SHA. Если обновление меняет требования или затрагиваемый код, применять только актуальную версию и прямо описать это в PR.
4. Если PR-ветка уже существует и `main` продвинулся, перед сдачей влить актуальный `main` в ту же ветку обычным merge, разрешить конфликты по текущим требованиям и повторно проверить затронутую область. Не создавать второй PR, не делать force-push и не переписывать историю rebase ради обновления base.
5. Непосредственно перед передачей PR владельцу ещё раз получить head SHA `main`, подтвердить, что PR не возвращает старые версии файлов и документов, и указать одновременно `current main SHA` и `head SHA` PR.

Фраза «main изменился только в документации» не отменяет обновление: документация содержит актуальные требования. Chatbot Agent обязан прочитать её и включить в свой текущий контекст до завершения кода.

## 4. Обязательный цикл

1. Codex выбирает следующий незавершённый Task ID с учётом зависимостей и готовит полную карточку по формату `CHATBOT-AGENTS.md`.
2. Codex передаёт карточку владельцу вместе с напоминанием Chatbot Agent прочитать `CHATBOT-AGENTS.md` до изменения кода.
3. Владелец отправляет карточку Chatbot Agent.
4. Chatbot Agent обновляет в своём контексте актуальный `main` по §3, изучает GitHub-код, создаёт отдельную ветку и Draft PR, затем перед сдачей ещё раз синхронизирует `main` и возвращает владельцу URL/current-main/base/head SHA и отчёт.
5. Владелец передаёт ответ и PR Codex.
6. Codex проверяет PR локально: исходную причину, целостный пользовательский путь, данные, права, offline/reload и узкие проверки по риску.
7. Codex исправляет найденные проблемы в той же PR-ветке. Дополнительный PR для исправлений review не создаётся.
8. Когда целевой путь технически проверен, Codex сливает PR в `main`, обновляет очередь и сообщает владельцу точный статус и оставшиеся ограничения.
9. Codex сразу выдаёт следующее задание. Цикл повторяется до завершения roadmap либо до продуктового решения, без которого безопасное продолжение невозможно.

## 5. Что означает завершение

Есть два отдельных состояния:

- **Технически интегрировано:** PR проверен Codex, необходимые исправления внесены, целевые проверки прошли, результат слит в `main`.
- **Принято владельцем:** владелец прошёл реальный сценарий на телефоне после удалённого развёртывания.

До этапа общего развёртывания отсутствие ручной проверки владельца не останавливает выдачу следующей задачи. Codex обязан прямо писать, какое из двух состояний достигнуто, и не выдавать merge или сборку за пользовательскую приёмку.

## 6. Формат передачи задания

Каждая карточка владельцу должна быть готова для копирования Chatbot Agent и содержать:

```text
Сначала прочитай CHATBOT-AGENTS.md и следуй ему без исключений.
Заново получи актуальный main из GitHub и не используй сохранённую в памяти копию файлов.

Task ID / название:
Roadmap item:
Checklist IDs:
Base: main @ <точный SHA>
Зависимости:
Проблема и воспроизведение:
Ожидаемый пользовательский результат:
Область изменений и исходные точки:
Не входит в задачу:
Offline / retry / reload / account switch / ACL / E2EE / TTL:
Критерии приёмки:
Что может проверить Chatbot Agent:
Что локально проверит Codex:

Создай отдельную ветку и Draft PR в main. Main не изменяй и не сливай.
Верни URL PR, base SHA, head SHA, список изменений и фактически выполненные проверки; недоступные проверки отметь NOT RUN.
```

Короткого сообщения «сделай R1-03» недостаточно: Chatbot Agent не видит локальное состояние и не должен угадывать критерии, границы или результаты предыдущего review.

## 7. Текущий переход

Физические устройства и финальная эксплуатационная приёмка остаются на этапе развёртывания.
