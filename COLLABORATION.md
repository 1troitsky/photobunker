# PhotoBunker — совместная работа и Scrumban

Этот документ задаёт рабочий цикл владельца, Codex и Chatbot Agent. Продукт и архитектура находятся в `docs/IMPLEMENTATION_PLAN.md`; оперативная очередь — только в GitHub Issues и GitHub Project **PhotoBunker Development**.

## 1. Роли

### Владелец

- определяет продуктовые приоритеты и принимает спорные решения;
- передаёт Chatbot Agent ссылку на подготовленный GitHub Issue;
- передаёт Codex ссылку на созданный PR;
- после удалённого развёртывания проверяет результат на телефоне и переводит его из `Integrated` в `Accepted`.

Владелец не обязан копировать длинные карточки, запускать команды или разбирать ветки.

### Codex

- ведёт GitHub Issues/Project и выбирает следующую готовую задачу;
- формулирует Issue с критериями приёмки, зависимостями и границами;
- проверяет PR локально, исправляет дефекты в той же ветке и выполняет узкие проверки по риску;
- сливает проверенный результат в `main`, переводит Issue в `Integrated` и готовит следующий Issue;
- не выдаёт merge, сборку или количество тестов за пользовательскую приёмку.

### Chatbot Agent

- перед каждым заданием заново читает актуальный `main`, `CHATBOT-AGENTS.md` и связанный Issue;
- работает только в `chatbot/<task-id>-<name>` и одном Draft PR;
- связывает PR с Issue через `Closes #<number>`;
- не изменяет и не сливает `main`, не включает auto-merge и не начинает следующую задачу самостоятельно;
- сообщает фактический base/head SHA и честно отмечает недоступные проверки как `NOT RUN`.

## 2. Источники истины

| Источник | Назначение |
| --- | --- |
| `docs/IMPLEMENTATION_PLAN.md` | продукт, архитектура, неизменяемые требования и долгосрочный roadmap |
| GitHub Issues | единственный операционный backlog, критерии конкретных задач и зависимости |
| GitHub Project | стадия работы, приоритет и видимость потока |
| Pull Request | реализация, review и фактические результаты проверок |
| `AGENTS.md`, этот файл, `CHATBOT-AGENTS.md` | постоянные правила команды |
| `docs/AUDIT-20261025.md`, `docs/CHECKLIST.md` | исходные требования и аудит, но не текущие статусы |
| `docs/REMEDIATION_PLAN-20261025.md` | архив перехода до Issues; новые карточки и статусы туда не добавляются |

Один и тот же статус или полный текст карточки нельзя параллельно поддерживать в Markdown и Issue.

## 3. Доска

Поле `Status` использует стадии:

`Backlog → Ready → In Progress → Review → Integrated → Accepted`

- `Backlog` — задача существует, но ещё не готова к реализации.
- `Ready` — выполнен Definition of Ready и зависимости интегрированы.
- `In Progress` — Chatbot Agent выполняет Issue и готовит Draft PR.
- `Review` — PR передан Codex для локальной проверки и доработки.
- `Integrated` — проверенный PR слит в `main`, но владелец ещё не принял его на реальном устройстве.
- `Accepted` — владелец принял сценарий после развёртывания.

Блокировка не заменяет стадию. Используются нативная связь Issue `blocked by`, метка `blocked` и короткая причина в комментарии. После снятия блокировки задача остаётся на прежней стадии.

Приоритеты: `priority:P0`, `priority:P1`, `priority:P2`, `priority:P3`. Область задаётся одной или несколькими метками `area:*`.

## 4. Definition of Ready

Issue можно переводить в `Ready`, только если:

- указан Task ID и ровно один основной пользовательский результат;
- дана ссылка на пункт roadmap/checklist;
- зависимости интегрированы либо оформлены через `blocked by`;
- описаны текущее и ожидаемое поведение, критерии приёмки и non-goals;
- определены применимые offline/reload/retry/account-switch/ACL/E2EE/TTL требования;
- задача достаточно мала для одного PR либо явно разделена на последовательные части;
- Chatbot Agent может начать работу от актуального `main` без скрытого продуктового решения.

## 5. Definition of Integrated и Accepted

`Integrated` означает одновременно:

- PR связан с Issue и не содержит постороннего scope;
- Codex проверил diff, источник отказа и целостный изменённый путь;
- найденные дефекты исправлены в той же ветке;
- прошли typecheck/build и узкие тесты/браузерная диагностика, необходимые по риску;
- миграции совместимы, права и приватные данные не ослаблены;
- PR слит в `main`, результаты и ограничения записаны в PR/Issue.

`Accepted` ставит владелец после реальной проверки на удалённом сервере/телефоне. До неё задача может быть `Integrated`, но не считается пользовательски принятой.

## 6. Обязательный цикл

1. Codex выбирает первый незаблокированный Issue в `Ready` с наибольшим приоритетом.
2. Владелец отправляет Chatbot Agent только ссылку и фразу: «Сначала прочитай `CHATBOT-AGENTS.md`, выполни этот Issue».
3. Chatbot Agent обновляет `main`, переводит работу в `In Progress`, создаёт ветку и Draft PR с `Closes #...`.
4. После передачи PR задача переходит в `Review`; владелец отправляет Codex ссылку на PR.
5. Codex проверяет и исправляет тот же PR, затем сливает его и переводит Issue в `Integrated`.
6. Следующий Issue выдаётся только после интеграции зависимости. Независимая параллельная задача требует явного решения Codex.
7. После развёртывания владелец проверяет сценарий и переводит Issue в `Accepted` либо возвращает его в `Ready` с конкретным дефектом.

## 7. WIP и конфликты

- Chatbot Agent: максимум одна задача `In Progress`.
- Codex: максимум один PR в активном `Review`.
- Обычно в работе не больше двух элементов: один реализуется, один проверяется.
- Нельзя параллельно менять одни и те же компоненты, API-контракты, миграционную цепочку или security boundary.
- Stacked PR, force-push и второй PR для замечаний review запрещены без явного решения Codex.
- Если `main` продвинулся, Chatbot Agent вливает актуальный `main` в свою ветку обычным merge и повторно проверяет затронутую область.

## 8. Автоматизация

GitHub автоматически добавляет Issues/PR в Project и выполняет безопасные переходы, доступные встроенным workflows. PR обязан ссылаться на Issue. Merge закрывает Issue и переводит технический результат в `Integrated`; `Accepted` никогда не выставляется автоматически.

Автоматизация не принимает продуктовые решения, не включает auto-merge, не отменяет локальный review Codex и не получает секреты приложения. OpenAI API-агент в GitHub Actions не используется, пока текущий CI не стабилен и владелец отдельно не согласовал стоимость и доступы.

## 9. Проверка процесса

После каждых четырёх `Integrated` задач Codex добавляет один короткий комментарий в Project/служебный Issue:

- время `Ready → Integrated`;
- число существенных исправлений на review;
- время/причина блокировок;
- один конкретный процессный эксперимент на следующие четыре задачи.

Не создаются спринты, ежедневные отчёты, отдельные status-файлы и метрики строк кода или количества тестов.
